# Web Serial の試作(#21)2026-11-18

## 結論
- **(2026-11-18)Linux の Chrome から、Web Serial で Tang Nano 9K の base デザインを操作できた(3 章)。** 識別値の確認、scratch の読み戻し、LED 6 個、ボタン 2 個が動き、往復は 2 ms で安定した。Python 側(1.87 ms)と変わらない。
- **パネルの方式として進めてよい(4 章)。** ただし確かめたのは Linux と 9K だけ。Windows は未確認。
- **プロトコルに足すべきものは、デザインの識別(5 章)。** ほかの候補は、今回は困らなかった。
- **通信の実装は小さい。** UARTBone の 1 ワードの読み書きは、JavaScript で 50 行ほど。Python 側と同じバイト列を送ることはテストで確かめた(2 章)。
- **Web Serial は `file://` で開いたページでも使える。** 試すだけなら Web サーバーは要らない。
- **未解決: LED 0〜5 のどれでもない LED が不規則に明滅する、という観察がある(3.1 章)。** 原因は未確認。

## 1. 作ったもの
- `examples/webserial/index.html`: 接続、`sys.id` の確認、scratch の書き込みと読み戻し、LED 6 個、ボタン 2 個(50 ms ごとに読む)、割り当ての無いアドレスの読み取り、ログ。ビルドも依存も無い。
- `examples/webserial/uartbone.js`: UARTBone の 1 ワードの読み書き。読み書きは 1 つずつ順に流す(ボタンの読み取りと LED の操作が同じ線を使うため)。
- `tests/test_webserial_js.py`: Node で上のモジュールを動かし、Python の `UARTBone` と送るバイト列を比べる。Node が無ければスキップする。

Python 側との違い:
- Web Serial には読み取りのタイムアウトも入力バッファの破棄も無い。ページ側で、受信をためる処理と、期限つきで待つ処理を持った。
- バーストは使っていない(1 ワードずつ)。

## 2. 実機なしで確かめたこと

## 2.1 実機で Python 側から確かめたこと(2026-11-18、Linux、Tang Nano 9K)
ブラウザと比べる基準として、`Overlay("base", board="tangnano9k")` で書き込み、同じ操作を Python から流した。UART は `/dev/ttyUSB1`(2 つのポートのうち後ろ)。

| 項目 | 結果 |
| --- | --- |
| `sys.id` / `sys.version` | `0x4e505131` / `0x00010000` |
| scratch に `0xcafef00d` を書いて読み戻す | 一致 |
| 書き込み直後の `leds` / `buttons` | `0x0` / `0x0` |
| `buttons` の読み取り 100 回の平均 | 1 回 1.87 ms |
| 割り当ての無いアドレス(`0x8000`、`0x3000`、`0x000c`、`0x1004`) | どれも `0xdeadbeef` が返る。エラーにもタイムアウトにもならない |

割り当ての無いアドレスは、決まった値 `0xdeadbeef` で見分けられる。ただし、本当にその値を持つレジスタとは区別できない。

### 3.1 未解決: 別の LED の明滅
操作中に、LED 0〜5 のどれでもない LED が不規則に明滅した、という観察がある。base デザインが駆動する LED は 6 個だけ(`gateware/boards/tangnano9k/top.v`、ピン 10、11、13〜16)で、ほかの LED を駆動する回路は無い。ページは 50 ms ごとにボタンを読むので、通信に連動している可能性がある。切り分けは未実施: ページの Disconnect を押して明滅が止まるかを見る。

## 4. パネルの方式として進めてよいか
進めてよい。理由:
- ブラウザだけで、識別、読み書き、周期的な読み取りが通った。
- 往復 2 ms は、パネルの部品を数十個並べて毎秒数回ずつ読むのに十分。
- ページ側で補ったのは、受信をためる処理と期限つきの待ちだけ。

残る確認: Windows(Zadig でドライバを替えた状態で UART のポートが残るか)、2 つのポートの見分け方、ケーブルを抜いたときの動き、3.1 章の明滅。
