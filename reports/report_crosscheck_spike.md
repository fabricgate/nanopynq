# 定義と回路の突き合わせの検査(試作)2026-11-19

issue #27 の「定義と回路を突き合わせる」の調査と試作。実機は使っていない(書き込みも通信もしていない)。
試作: `tools/p0/crosscheck.py`。テスト: `tests/test_crosscheck.py`(`-m toolchain`)。

## 結論
- **実機なし・YoWASP の yosys だけで、合成の前に検査できる。方法は `sat`(有界のモデル検査)。**
  - ホストのブリッジ(`uartbone_bridge` / `jtag_bridge`)を、小さなバスのマスター(読む → 書く → 読む)に差し替える。
  - 平らにした回路で `sat -seq 32 -prove` を使う。
  - 時間: 9K の base は 2.9 秒、base + `pwm_timer` は 8.1 秒(4 プロセス並列)。1 プロセスなら 8.3 秒と 27.0 秒。
- **YoWASP の yosys 0.70 には `sim` コマンドが無い。** `sim` で刺激を流す方法は、利用者の環境では使えない。
- **見つけられるもの(エラー):**
  - (a) 定義のアドレスにスレーブがいない。
  - (b) 定義に無いアドレスが応答する。代表点ではなく、**全アドレスをまとめて証明**する。反例から、応答した番地が分かる。
  - わざと食い違わせたもののうち、次はエラーで止まった: ベースアドレスのずれ(定義の側でも RTL の側でも)、レジスタの書き漏らし、回路に無いレジスタ、IP の書き漏らし。
- **警告にとどめるもの:** (c) `rw` / `ro` の取り違えと、幅の取り違え。どちらも見つかる。警告にした理由: 仕様 5.3 の `rw` は、書いた値が読み戻せることまでは約束していない。4K の spiflash の `data` は、書くと送信し、読むと受信した値が返る。この検査は、これを誤りとして報告した。
- **見逃すもの:** `ro` の幅を実際より広く書いた場合 / `wo` のアクセスの誤り / 2 つのスレーブが同じ番地に応答する重なり / 広い窓で 0 を返すスレーブの中に、でたらめなレジスタを書いた場合 / 値の意味。
- **利用者の top に求める決まりは、ほぼ 1 つ。** nanopynq のブリッジの実体が 1 個あること。バスの信号名には決まりを求めない。加えて、リセットが設定から約 20 クロック以内に終わること。入力ピンがリセットに入っている top は、その入力を固定する指定が要る。これらを満たさない top は「検査できない」で止まる(黙って通さない)。
- **勧める形:** `nanopynq build` の中で、識別値の計算の前に既定で走らせる。エラーなら止まる。検査を飛ばすオプションを用意し、飛ばしたら表示する(7 章)。

## 1. 実行した環境と、確かめた yosys の挙動
- yowasp-yosys 0.70.0.0.post1259(`Yosys 0.70 (git sha1 28ba3cb92)`)。`uv sync --extra build` で入ったもの。PC は 32 コアの Linux。
- **`sim` が無い(事実)。** `yowasp-yosys -p "help sim"` は `No such command or cell type: sim`、`sim -clock clk -n 4` は `ERROR: No such command: sim`。`help` の一覧にも無い。あるのは `eval`(組み合わせ回路だけ)、`sat`、`write_cxxrtl`、`write_simplec`、`write_smt2`、`write_btor`、`write_aiger`。
- **`yowasp-yosys-smtbmc` と `yowasp-sby` は入っているが、使う SMT ソルバーが無い。** `yices`、`z3`、`boolector`、`bitwuzla` は、どれも PATH に無い。
- **`sat` について確かめた事実:**
  - `-seq N` で N クロック分を展開する。`-set`(全時刻)、`-set-at`、`-prove`、`-prove-skip`、`-show` が使える。
  - 結果は `SAT proof finished - no model found: SUCCESS!` か `... model found: FAIL!` の行に出る。反例は `-show` の表に出る。
  - `init` 属性は、初期状態として取り込まれる(ログに `Import set-constraint from init attribute: \por = 5'00000`)。初期値の無いレジスタは、自由な値になる。
  - `(* anyconst *)` を付けたレジスタは、展開した全時刻で同じ値だった。`-set` で固定することも、自由にしておくこと(全アドレスの証明)もできる。
- **落とし穴(事実):** 最初は、初期値を持たず自分自身を保持するレジスタ(`a <= a`)で番地を持たせた。`opt -full` のあと、試した 3 つの問い合わせ(1 つは FAIL になるはずのもの)が、すべて SUCCESS になった。`opt_dff` が `Handling D = Q ... (removing D path)` で FF を消し、線を `30'x` につなぐ。`sat` は x を 0 として扱うので、`-set npq_a 5` は前提が矛盾して解が無くなり、どの証明も「成り立つ」になる(空の証明)。`$anyconst` に変えて直した。**レジスタごとの (a) の問い合わせは、この種の空の証明に気づく仕掛けになる**(空なら、すべてのレジスタを `no_slave` と報告する)。このため、(a) はまとめずに、レジスタごとに残す。

### 2.1 候補 1 の代わり: `sat` で UART の刺激を再生する
- 9K の top の写しで `BAUD` を `6_750_000`(1 ビット 4 クロック)にし、読み取りのフレーム(`02 01 00 00 00 00`)を 1 ビットずつ `-set-at <t> uart_rx <v>` で 524 ステップ分与えた。`-show uart_tx` の波形を復号すると `4e 50 51 31`(`NPQ1`)が出た。先頭に `ff` が 1 つ付いた(リセット前の `uart_tx` の不定な値と推定。確かめていない)。
- 時間は `sat` だけで 11.5 秒(読み取り 1 回)。本来のボーレート(1 ビット約 234 クロック)では、1 回が約 2 万 4 千ステップになり、数百秒かかる見込み(推定)。
- **`chparam` では速くできない(事実)。** `chparam -set BAUD 6750000 base_soc` のあとの `uart_rx` の派生は、指定しないときと同じだった。9K の top が `.BAUD(115200)` を直に渡しているため。
- 結論: ブリッジまで含めて確かめられることは示せたが、毎回のビルドには遅すぎる。ブリッジは共通の部品で、`gateware/sim` で試験されている。検査は、ブリッジを差し替えた位置(候補 3)で行う。

### 2.2 候補 4: 構造から読む
- 9K + pwm を `proc; flatten; opt -full` にかけ、`write_json` の中から、top の `adr` の線を入力に持つ比較のセルを拾った。`adr == 0x800`、`adr == 0x400`、`adr == 0x2`、`adr <= 3`、`adr >= 0x1c00` と `$sub`、`adr[2:0] == 1/2/3` が拾えた。
- 比較が「応答する範囲」なのか、「書き込みの条件」なのか、「読み出しの選択」なのかは、構造からは分からない。引き算・比較・`case` から範囲を復元するのは、ソルバーを作り直すことになる。バスの線を見つけるのに、名前の決まりも要る。採らない。

### 2.3 候補 5: 実機での確認(比較の対象として)
- 強み: (a) の確かさは高い。`sat` の結果の最終の確認にもなる。
- 弱み: 合成と書き込みのあとにしか分からない。実機が要る。`wo` と `read_effect` のレジスタは読めない。(b) は 1 番地ずつ読むことになり、全範囲は現実的でない(推定)。
- 試作していない。補助として、将来サブコマンド(書き込み直後の確認)にする価値はある。

## 3. 勧める方法(候補 3)の仕組み
1. **差し替え。** 利用者のソースを読んだあと、`read_verilog -overwrite` で `uartbone_bridge` と `jtag_bridge` を上書きする。差し替え版は、同じポートとパラメータを持ち、中に `npqchk_master` を持つ。
2. **マスターの動作。** リセットが解けたら、同じ番地 A に対して「読む(r1)→ W を書く → 読む(r2)」を行う。決まりはブリッジと同じ(`stb` を `ack` まで保持)。A、W、マスクは `$anyconst`。
3. **前処理。** Gowin のセルライブラリを `-lib` で読み、`hierarchy -check; proc; flatten; cutpoint -blackbox; async2sync; memory -nomap; cutpoint t:$mem_v2; opt -full; opt_clean`。黒箱(4K の `GW_JTAG` などのプリミティブ)の出力と、メモリの読み出しは、自由な値にする。メモリを FF に展開すると、4K の camera(20 KiB のバッファ)で yosys の WASM が例外で落ちた(72 秒後)。自由化したあとは 19.4 秒で終わった。
4. **差し替えの場所を探す。** `select -list w:*npqchk_done` で探す。0 個か 2 個以上なら「検査できない」にする。
5. **問い合わせ。** 1 回の問い合わせごとに `sat -seq 32 -prove ...` を実行する。`design.il` を読み直した yosys を 4 個並列に動かす。`SUCCESS!` / `FAIL!` の行が無ければ、例外にする(黙って通さない)。

| 問い合わせ | 量化 | 期待 | 違ったとき |
| --- | --- | --- | --- |
| (done) 全番地で、3 回のやり取りが 32 クロック以内に終わる | すべての番地 | 証明できる | **エラー**「検査できない」(反例の番地を示す) |
| (a) 定義のレジスタごとに、r1 が `0xdeadbeef` でない実行がある | 存在 | 反例がある | **エラー** `no_slave` |
| (b) IP の範囲ごとに、定義に無い番地はすべて `0xdeadbeef` | すべての番地 | 証明できる | **エラー** `undeclared`(番地と値)。IP が `addr_range` か `streams` を持てば警告 |
| (b') どの IP の範囲にも無い番地は、すべて `0xdeadbeef` | すべての番地 | 証明できる | **エラー** `outside` |
| (c) `rw`: すべての W で r2 == W & マスク(幅) | すべての W | 証明できる | 警告 `not_rw`(書いた値と読んだ値) |
| (c) `ro`: 上の性質が成り立たない | — | 反例がある | 警告 `not_ro` |
| (c) `ro`: r1 の幅を超えるビットが 0 | すべての実行 | 証明できる | 警告 `width` |

- `wo` は (a) だけを行う。`read_effect` は見ない(検査の中なので、読んでも害は無い)。
- (a) で `0xdeadbeef` を報告したものは、(c) で重ねて報告しない。
- `inputs`: top の入力を、検査のあいだ固定する(例: `{"btn": 0}`)。それ以外の入力は自由な値のまま。
- 注意: 既定値と同じ `addr_range: "0x1000"` を明示しただけでも、(b) が警告に下がる。

## 5. 見つけられる食い違いと、見逃す食い違い
9K + pwm_timer に対して試した(`tests/test_crosscheck.py`)。

| 食い違い | 結果 | 文面(抜粋) |
| --- | --- | --- |
| 定義の `pwm.base` を 0x7100 にする(RTL は 0x7000) | **エラー** | `ips.pwm.registers.ctrl(0x7100): 読むと必ず 0xdeadbeef が返る。この番地に応答するスレーブが回路に無い`(5 レジスタすべて)と `0x700c: どの IP の範囲にも無い番地が応答する` |
| RTL の側を 0x7100 にする | **エラー** | `no_slave` と `0x71xx: IP pwm の範囲で、定義に無い番地が応答する` |
| `pwm.wraps` を書き漏らす | **エラー** | `0x7010: IP pwm の範囲で、定義に無い番地が応答する(読んだ値 0x00000000)。レジスタを定義に書き漏らしていないか` |
| 回路に無い `pwm.extra`(0x14)を足す | **エラー** | `ips.pwm.registers.extra(0x7014): 読むと必ず 0xdeadbeef が返る` |
| IP `pwm` を丸ごと書き漏らす | **エラー** | `0x7000: どの IP の範囲にも無い番地が応答する` |
| `count`(ro)を `rw` と書く | 警告 | `rw・幅 32 ビットと定義したが、0x00000001 を書いて読むと 0x00000000` |
| `period`(rw)を `ro` と書く | 警告 | `ro と定義したが、書いた値がそのまま読み戻せる。rw ではないか` |
| `leds.data`(rw、6 ビット)を 8 ビットと書く | 警告 | `0x0000007f を書いて読むと 0x0000003f` |
| `period`(rw、32 ビット)を 16 ビットと書く | 警告 | `0x00200000 を書いて読むと 0x00200000(期待 0x00000000)` |
| `sys.id`(ro)を 16 ビットと書く | 警告 | `幅 16 ビットと定義したが、上位のビットが 1 で返る(0x4e505131)` |
| `buttons.data`(ro、2 ビット)を 1 ビットと書く | 警告 | 上位のビットが 1(入力は自由な値なので、反例が見つかる) |
| `buttons.data` を 4 ビットと書く(実際より広い) | **見逃す** | 上位が 0 なのは、正しい値でもあり得る |
| リセットが長い・`ack` が遅い(depth 20 で再現) | **エラー**「検査できない」 | `設定から 20 クロックのうちに、番地 0xc の読み書きが終わらない` |
| リセットにボタンの入力が入っている | **エラー**「検査できない」。`inputs={"btn": 0}` で通る | 同上 |
| 標準のブリッジを使わない top | **エラー**「検査できない」 | `ホストのブリッジ(uartbone_bridge か jtag_bridge)の実体が 0 個ある` |

ほかに見逃すもの(推定を含む):
- リセット直後に上位が 0 の `ro`(カウンタなど)は、幅を狭く書いても見逃すことがある。
- `wo` の取り違え(`wo` は (a) しか見ない)。
- 重なり。2 つのスレーブが同じ番地に応答しても、どちらも `0xdeadbeef` ではないので見逃す。
- 広い窓で 0 を返すスレーブの中の、でたらめなレジスタ。(a) は通る。その IP に `addr_range` も `streams` も無ければ、(b) がエラーになるので気づく。ある場合は警告だけ。
- 状態に依存するデコード。事前の設定が要る応答は、(a) で `no_slave` と誤って報告されることがある。
- 値の意味、副作用、`read_effect` の正しさは見ない。
- 黒箱の出力は、自由な値として扱う。PLL のロックをリセットに使う top は「検査できない」になる見込み(推定。4K の pllcheck は通った)。

## 6. 利用者の top に求める決まり
1. **nanopynq のブリッジ(`uartbone_bridge` か `jtag_bridge`)の実体が、ちょうど 1 個あること。** `base_soc` 経由でもよい。モジュール名を変えた写しは不可。スレーブはそのバスにつなぐ。バスの信号名や属性の決まりは要らない。
2. **割り当ての無い番地は `0xdeadbeef` を返すこと。** `base_regs` を使えば満たす。
3. **リセットが、設定から depth − 約 10 クロック以内に終わること。** 9K の top(16 クロックの power-on リセット)では、やり取りは 26 クロック目に終わる。入力ピンがリセットに入っていれば、その入力を `inputs` で固定する。
4. 試作が作る `npqchk_*` という名前を、利用者が使わないこと。

## 7. 本体に組み込むときの形(案)
```python
def crosscheck(ips: dict, sources: list[Path], top: str, board: str, *, out_dir: Path,
               depth: int = 32, workers: int = 4, inputs: dict[str, int] | None = None) -> CrosscheckResult
# CrosscheckResult: ok, errors: list[Problem], warnings: list[Problem], queries, seconds
# Problem: where ("ips.pwm.registers.ctrl" か "0x7010"), kind, message
```
- 呼ぶ場所: `ips` の検査(V1〜V10)のあと、識別値の計算の前。
- エラーのとき: 止まる。すべての問題を並べ、定義か RTL を直すよう案内する。警告は表示して続ける。
- 検査を飛ばす手段: 用意することを勧める。6 章の決まりを満たさない top(自作のブリッジ、長いリセット)でもビルドできるようにするため。飛ばしたことは表示する。`.npq` には書かない(仕様の項目を増やさないため)。
- `nanopynq.toml` に足すもの: `inputs`(固定する入力)と `depth`。どちらも省ける。
- 出力: `design.il` と問い合わせごとのログを、ビルドのフォルダに置く(反例を見たい人のため)。
- 本体に移すときに直すこと: 内部の関数 `nanopynq.build.gowin._tool_path` を借りている / ボードからの族(`gw1n` / `gw2a`)の選択を `boards.yaml` から引く / `SUCCESS!` / `FAIL!` の行が無ければ例外にする判定は、本体でも保つ。
- テスト: **通るべきでないものが止まることを、必ず確かめる**(1 章の落とし穴は、通るべきものだけでは気づけなかった)。

## 8. 確かめられなかったこと
- 実機での比較(候補 5)。
- Windows と macOS での時間。コアの少ない PC での時間(並列の効果)。
- `yowasp-sby` の `abc` エンジンが動くか(SMT ソルバーが無いことだけを確かめた)。
- `ack` が複数クロック遅れる利用者のスレーブや、状態に依存するデコードでの挙動(depth の余裕は 6 クロック)。
- PLL のロックをリセットに使う top(推定だけ。入力ピンでのみ確かめた)。
- `uart_tx` の復号の先頭の `ff` の原因(推定だけ)。
