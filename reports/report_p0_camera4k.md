# Tang Nano 4K のカメラを nanopynq から扱うための P0（2026-11-03）

## 結論
- 4K に付いているカメラは OV2640（PID 0x2642、製造者 ID 0x7FA2）。FPGA から XCLK を出し、ホストから SCCB を操作して読めた。
- OV2640 は、リセットの後は DVP の出力（PCLK、HSYNC、VSYNC）を駆動しない（ハイインピーダンス）。DSP の 0x2C=0xFF、0x2E=0xDF を書くと出力が有効になり、PCLK と HSYNC と VSYNC が動き出した。
- 手元で直したオープンなツール（4K の土台と同じもの）で、PLL（PLLVR）と、2 つのクロックで使う 16 KB の BSRAM を配置できた（ビルドだけの確認）。
- JTAG の読み出しは、N 語を 1 回の USB の往復で送ると毎秒約 11000〜12000 語（約 45〜49 kB/s）になった。今の1語ずつ（毎秒約 2100 語）の約 5 倍。1 回の転送の応答は約 1 KB が上限で、それを超えると応答が途中で切れる（128 語で 1161 バイト中 1024 バイト）。
- したがって、QQVGA（160×120）のグレー 1 枚（19.2 kB）は約 0.4 秒で読める見込み（計算）。

## 1. カメラのピン（回路図 Tang_Nano_4K_3603 の1ページ目）
| 信号 | FPGA のピン | バンク（電圧） | カメラの端子 P3 |
|---|---|---|---|
| PIXDATA0 | 22 | 3（1.8 V） | 24（FB_SDA と表記） |
| PIXDATA1 | 21 | 3 | 23（FC_SDA と表記） |
| PIXDATA2 | 17 | 3 | 19（D0） |
| PIXDATA3 | 19 | 3 | 21（D1） |
| PIXDATA4 | 20 | 3 | 22（D2） |
| PIXDATA5 | 18 | 3 | 20（D3） |
| PIXDATA6 | 16 | 3 | 18（D4） |
| PIXDATA7 | 23 | 3 | 16（D5） |
| PIXDATA8 | 39 | 1（3.3 V） | 14（D6） |
| PIXDATA9 | 40 | 1 | 12（D7） |
| DVP_PCLK | 41（GCLKT_1） | 1 | 17 |
| DVP_HSYNC | 42 | 1 | 9 |
| DVP_VSYNC | 43 | 1 | 7 |
| CAMERA_SCL | 44 | 1 | 5 |
| CAMERA_SDA | 46 | 1 | 3 |
| DVP_XCLK | 33（GCLKC_2） | 2（2.5 V） | 13（MCLK） |
- カメラの IO の電源（DOVDD）と SCCB のプルアップ（4.7 kΩ）は 2.5 V。
- RESET は RC（100 kΩ と 10 µF）、PWDN は 4.7 kΩ で GND。どちらも FPGA からは動かせない。
- 8 ビットで使うときは PIXDATA2〜9（端子の D0〜D7）。

## 2. 実機での確認（`tools/p0/cam4k/sccb_probe_top.v`、`sccb_probe.py`）
- 試験用の top は、土台の部品（jtag_bridge、base_regs）だけで作った。LED の出力のビットで SCL と SDA を引き下げ、XCLK（27 MHz の 2 分周 = 13.5 MHz）を出す。ボタンの入力のビットで SCL、SDA、VSYNC、HSYNC、PCLK を読む。
- SCCB は、ホストからレジスタの読み書きで1ビットずつ動かした。
- 結果:
  - XCLK を止めると SCCB は応答しない（ACK が返らない）。XCLK を出すと応答する。
  - センサーのバンク（0xFF=0x01）の 0x0A/0x0B = 0x26/0x42、0x1C/0x1D = 0x7F/0xA2。
  - リセットの後は PCLK、HSYNC、VSYNC が動かない。FPGA 側でプルアップを掛けると 1 が読めたので、駆動されていない（ハイインピーダンス）。
  - DSP のバンク（0xFF=0x00）の 0xE0（RESET）は 0x04（DVP がリセットされたまま）。0 を書いても出力は動かなかった。
  - Linux の ov2640 ドライバの初期化表の先頭を1つずつ書くと、DSP の 0x2C=0xFF、0x2E=0xDF を書いた直後に、PCLK（約半分が 1、変化が多い）、HSYNC（約 8 割が 1）、VSYNC（短いパルス、毎秒 8 回前後と推定）が動き出した。この2つのレジスタの意味は公開資料に書かれていない（Linux のドライバでも名前が付いていない）。

## 3. PLL と BSRAM（`tools/p0/cam4k/bsram_pll_check.v`、ビルドだけ）
- PLL の設定値は `python -m apycula.gowin_pll -d "GW1NSR-4C C7/I6" -i 27 -o 54` で作った（PLLVR）。
- 54 MHz で書き、27 MHz で読む 8 ビット × 16384 のメモリは BSRAM 8/10 に収まった。PLLVR は 1/2。タイミング違反なし。
- BSRAM は全部で 10 個（1 個 2 KB、合わせて 20 KB）。QQVGA のグレー（19.2 kB）は全部を使う。JTAG ブリッジなど他の回路は BSRAM を使っていない。
- 実機での読み書き（中身が正しいか）は確かめていない。

## 4. まとめて送る読み出しの速さ（`tools/p0/cam4k/batch_speed.py`）
| 1 回の転送でまとめた語数 | 速さ |
|---|---|
| 1 | 2105 語/秒（8.4 kB/s） |
| 4 | 6065 語/秒 |
| 16 | 10179 語/秒 |
| 32 | 11092 語/秒 |
| 64 | 11300 語/秒 |
| 100 | 12245 語/秒（49.0 kB/s） |
| 112 | 11552 語/秒 |
| 128 | 失敗（応答が 1024 バイトで止まる） |
- 1 語の DR スキャンの応答は 9 バイトなので、1 回の転送は約 110 語までにする必要がある。
- 失敗の後も BL702 は固まらず、次の実行は普通に動いた。

## 5. PSRAM（調べただけ）
- Apicula 0.35 の `chipdb_builder.py` に、GW1NSR-4C の内蔵 HyperRAM のピン（`O_hpram_ck`、`IO_hpram_dq` など）の定義がある。制御の回路は自前で作る必要があり、オープンなツールで動くかは確かめていない。

## 6. 確かめられなかったこと
- 画素のデータ（PIXDATA）が正しく読めるか。今回は PCLK、HSYNC、VSYNC の動きだけを見た。
- OV2640 の解像度、出力の形式（YUV、RGB、JPEG）の設定。初期化表の残りが要る。初期化表は Linux のドライバ（GPL-2.0）のものを試しに使っただけで、リポジトリには入れていない。同梱するなら、出どころとライセンスを決める必要がある。
- BSRAM の実機での中身、PLL の実機での周波数。
