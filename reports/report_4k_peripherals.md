# Tang Nano 4K のペリフェラルの確認（2026-11-05）

## 結論（途中経過）
- カメラを付けたまま自由に使えるピンは **13 だけ**（Bank3、1.8 V）。ピン 8 は JTAGSEL_N なので GPIO にしない。PWM やタイマーを外に出す先は、実質 LED だけになる。
- **チェックリストの 1〜6 がすべて済んだ**（オープンなツールだけで）: PLL（3.1）、HDMI のテスト画面（3.2）、PWM / タイマー（3.3）、SPI フラッシュ（3.4）、PSRAM を CK 20.25 MHz まで（3.5）、カメラ → PSRAM → HDMI（3.6、160×120 を 640×480 に 4 倍で、毎秒 8 枚の更新）。
- **チェックリストの 7 も済んだ**（3.7）: 2 つ目の PLL（81 MHz）で PSRAM を動かし、320×240 を 2 倍で 640×480 に出した（毎秒 8.66 枚の更新、HDMI 60 fps）。途中で、遅れて ack する slave がこのバスでは読めない（ほかの slave が先に 0 で ack する）ことが分かり、top で直した。
- 上流の候補が 1 つ増えた: Apicula の圧縮のキーに 0x00 が入ると、openFPGALoader が書き込みを拒む（3.5）。
- ユーザーフラッシュ（256Kb = 32 KB）は、Cortex-M3 のプログラム用のフラッシュ（FLASH256K）だと分かった（2 章）。
- **チェックリストの 8（ユーザーフラッシュの読み出し）は、実機の前で止めた**（3.8）。いまの道具で M3 なしにビルドすると、PROG / ERASE / NVSTR の 3 本に、実際は 1 が入る（nextpnr がすべてのピンに反転を入れるため）。Gowin の IDE は、このチップで M3 なしの FLASH256K を拒む（PA2090）。UG295 も「MCU 用」と書いている。読み出しの回路と sim は残した。
  - 実機（段階 1〜3）: EMCU を置けば M3 はフラッシュのファームウェア（`openFPGALoader --mcufw` で書いた）で動く。IDE 版も Apicula 版も。**ただし、ファブリックからはユーザーフラッシュを読めない**（DOUT は M3 にだけ届き、ファブリック側は 0）。
  - 影響範囲: IDE と比べた中では、書き込みと消去のピンが逆になるのは GW1NS-4 だけ（1K / 9K は IDE も反転していて、nextpnr と合う）。EMCU を置けば、Apicula のビットストリームは IDE と同じ形になり、DOUT もファブリックから読める（ビルドで確認、実機はまだ）。
- デバッガー（BL702）が固まったとき、`tools/usb_recover.py` では直らないことがある。抜き差しが要る（4 章）。

- [x] 2. HDMI 出力（まず 640×480 のテスト画面）: TLVDS_OBUF + OSER10 + CLKDIV
- [x] 3. PSRAM を速くする（いまは CK 6.75 MHz）。HDMI に PSRAM から絵を出すための帯域

- [x] 4. カメラ → PSRAM → HDMI（3.6）
  - 合格: HDMI が約 60 fps、キャプチャボードで取り込んだ絵が一様でなく、2 回取り込むと違う（カメラの絵が動いている）。ホストへの取り込み（camstream）は変えない
- [x] 5. タイマー / PWM（LED で確認）
  - 合格: PWM の出力を周波数計で数えて設定どおり（±1）、周期の回数のレジスタが時間と合う。デューティーは sim で確かめる
- [x] 6. SPI フラッシュ（P25Q32、32 Mbit）の読み書き。ピン 8（WP と JTAGSEL_N の兼用）は触らない
  - 合格: JEDEC ID が P25Q32 の値、同じ場所を 2 回読んで同じ、全部 0xFF の区画だけを消して書いて読み戻して一致。空いた区画が無ければ止める
- [x] 7. カメラの絵を大きくする（3.7）: 4 の回路の PSRAM 制御器を 3.5 の速いクロック（×2 か ×3）で動かし、160×120 より大きいフレーム（目標 320×240 を 2 倍で 640×480）を出す
  - 合格: 4 と同じ確認（HDMI 約 60 fps、BAD 0、2 回の取り込みが違う）に加えて、1280×960 の取り込みで隣り合う画素の差が 4 の周期に集中する（ソースの 1 画素が 4×4）。PSRAM の往復（`hram_burst.py`）もその速さで不一致 0
- [ ] 8. ユーザーフラッシュ（FLASH256K）の読み出し。書き込みと消去はしない（PROG / ERASE / NVSTR は回路の中で 0 に固定し、バスに出さない）
  - 合格: Apicula で FLASH256K を使ったビルドが通る、32 KB（32 ビット × 8192 語、XADR 7 ビット × YADR 6 ビット）を 2 回読んで同じ。読み出しのタイミングは、先に資料で確かめる
  - 追加（2026-11-06）: 中身が一定の値（全部 0 など）なら「判定できない」とする。空のフラッシュと、DOUT の配線の誤りを区別できないため
  - **止めた（2026-11-06、3.8）**: M3 なしのビルドは、PROG / ERASE / NVSTR に 1 が入るビットストリームになる（実機には載せていない）。EMCU を置いた形は安全で、M3 はフラッシュのファームウェアで動くが、ファブリックから読むと 0。このチップでは、ファブリックからは読めない
- 外したもの: ユーザーフラッシュへの書き込み（FPGA の設定用の領域との関係が分からないうち）、ADC（無い）、Cortex-M3（方針外。2 章）、MIPI / I3C（使い道が無い）

## 3. 確認の記録

### 3.1 PLL（2026-11-05、合格）
- 回路は `gateware/boards/tangnano4k/pll_top.v`。土台の回路に PLLVR と、周波数計 `gateware/rtl/clk_meter.v`（0x5000）を足した。周波数計のテストは `gateware/sim/test_clk_meter.py`（3 件、合格）。
- ビルドは `tools/build_base.py --design pllcheck --out DIR`、実機の確認は `tools/p0/pll4k/pll_check.py DIR`。
- 測り方: 27 MHz で 2 700 000 サイクル（100 ms）のゲートを作り、その間の各クロックのエッジを数える。両方とも同じ水晶から作るので、ずれは PLL か道具の誤り。
- 配置配線の最高周波数: 126 MHz の側 188 MHz、27 MHz の側 103 MHz（どちらも余裕あり）。

**結果（VCO 1008 MHz の設定、5 回読んで全部同じ）**
| 出力 | 期待するカウント | 実測 |
|---|---|---|
| CLKOUT 126 MHz | 12 600 000 | 12 600 000 |
| CLKDIV で 5 分周 25.2 MHz | 2 520 000 | 2 519 999〜2 520 001 |
| CLKOUTD（SDIV 4）31.5 MHz | 3 150 000 | 3 150 000 |

LOCK は 1。CLKOUTD は Apicula の例では使われていないが、正しく動いた。

**最初の失敗と原因**
- 最初は `apycula.gowin_pll -d "GW1NSR-4C C7/I6" -i 27 -o 126` の設定（IDIV 3、FBDIV 14、ODIV 4、VCO 504 MHz）にした。
- 結果は、LOCK が 0 のまま。CLKOUT は約 128.7 MHz で漂い、CLKOUTD はそのちょうど 1/4 だった。VCO が約 515 MHz で自走していたことになる。
- 同じ設定を Gowin の IDE（V1.9.11.03 Education、GW1NSR-LV4CQN48PC6/I5）で合成すると、`ERROR (EX0311) : Invalid VCO frequency … suitable range is from 600MHz to 1200MHz` で止まった。
- ODIV を 8 にする（VCO 1008 MHz、出力は同じ 126 MHz）変更 1 つで、ロックし、カウントも合った。
- **原因: VCO を、実際の下限より低く設定していた。**
  - Apicula の `gowin_pll` の表は、GW1NSR-4C の VCO の下限を 400 MHz としている（C7/I6 も C6/I5 も。注記は「Untested」）。`gowin_pack` の `GW1NS_4.get_permitted_pll_freqs` も 400。
  - 調査担当のエージェントが読んだ DS861-1.6.2（中国語版）も 400–1200 としている。
  - しかし IDE は 600 未満を拒否し、実機では 504 でロックしなかった。
  - 本当の下限が 600 なのか、515 付近なのかは確かめていない。
- **影響**: 以前ビルドだけ確かめたカメラ用の PLL の設定（`tools/p0/cam4k/bsram_pll_check.v`、54 MHz、VCO 432 MHz）も、同じ理由でロックしないはず。
- **上流に報告した**: YosysHQ/apicula#580（2026-11-05）。Apicula の `gowin_pll.py` と `gowin_pack.py` の GW1NSR-4C の VCO の下限（400 → 600）。
  - 出す前に確かめ直した: 上流の master 86d65b1 の `gowin_pll` も VCO 504 MHz の設定を出す。IDE の EX0311 も再現。
  - 実機（PR のブランチの道具）で、504 MHz では CLKOUT が 128.19〜128.26 MHz、記録した 13 回の読み出しのうち 12 回で LOCK が 0。上の「LOCK が 0 のまま」は、正しくは「ほぼ 0 で、まれに一瞬 1」。

**決めたこと**: 4K の PLL は VCO を 600 MHz 以上にする。設定値を `gowin_pll` で作るときは、VCO の値を必ず確かめる。

### 3.2 HDMI 出力（2026-11-05、合格）
**構成**
- 回路は `gateware/boards/tangnano4k/hdmi_top.v` と `hdmi.cst`。
- 部品は `gateware/rtl/tmds_encoder.v`、`video_timing.v`、`hdmi_testpat.v`（0x6000）。
- クロック: PLLVR で 126 MHz（VCO 1008 MHz）、CLKDIV で 5 分周した 25.2 MHz を画素のクロックにする。
- 出力: OSER10（DDR で 252 Mbit/s）を 4 本、Bank2 の TLVDS_OBUF に出す。
- レジスタ: CTRL（0 = カラーバーに 1 ピクセルの白い枠、1 = 単色）、COLOR、FRAMES（送ったフレームの数）。

**シミュレーション**（`gateware/sim/test_video.py`、3 件、合格）
- TMDS 符号化器: DVI 1.0 の Python のモデルと 3004 語が一致し、復号すると元に戻る。累積の偏りは ±10 以内。
- タイミング: 800 × 525、hsync 96、vsync 2 ライン。
- テスト画面: 1 フレーム 480 ラインを復号して、枠とバーの色を確認。単色の切り替え、FRAMES も確認。
- 途中で見つけた誤り: リセット中は h = v = 0 のままなので、`frame_start` が出っぱなしになり、FRAMES がリセット中に数を重ねていた。`video_timing` で、リセット中は `de` と `frame_start` を 0 にして直した。テストは FRAMES の絶対値（ちょうど 1）で確かめる形にした。

**ビルド**
- 画素のクロックの最高周波数は 58 MHz（必要なのは 25.2）。
- 126 MHz の側は OSER10 だけで、論理回路は無い。

**実機**（`tools/p0/hdmi4k/hdmi_check.py`）
- FRAMES から 59.9 fps（2.00 秒で 120 フレーム、期待値は 60.0）。画素のクロックとタイミングは、実機で期待どおりに動いている。
- HDMI のキャプチャボード（UGREEN 25773、USB カメラとして見える）につなぎ、ffmpeg で取り込んで画素を数えた。
  - カラーバー: 左から白、黄、シアン、緑、マゼンタ、赤、青、黒の 8 本が、正しい順と幅で映った。1280×960（ちょうど 2 倍）で取り込むと、帯の境目は 160 画素おきで、横のずれは無い。右端の白い枠も写る。
  - 単色（CTRL = 1、COLOR = 0x123456）: 画面全体が同じ値 (4, 42, 75) になった。値が送った (18, 52, 86) と違うのは、キャプチャボードが RGB を 16〜235 の範囲として読んで広げるため（緑は (52 − 16) × 255 / 219 ≈ 42 で一致）。
- **キャプチャボードでは、縦に 1 ライン下にずれる**: 一番上に黒が 1 ライン、その下に白い枠（ライン 0）があり、下の白い枠（ライン 479）は写らない。
  - DE の 480 ラインのうち最初と最後が白いことは、シミュレーションで確かめてある。タイミングも VESA の 640×480 の標準どおり（フロントポーチ 10、同期 2、バックポーチ 33）。
  - なので、キャプチャボードが絵の始まりを DE ではなく同期から決めているためと推定（確かめていない）。ほかのモニターでは見ていない。

### 3.3 タイマー / PWM（2026-11-05、合格）
- 部品は `gateware/rtl/pwm_timer.v`（0x7000）。
  - レジスタ: CTRL（有効）、PERIOD（周期のクロック数）、DUTY（High のクロック数）、COUNT（周期の中の位置）、WRAPS（有効にしてから終えた周期の数。これがタイマー）。
  - PERIOD と DUTY の書き換えは次の周期の頭で効く（途中の半端なパルスを出さない）。
- 回路は `gateware/boards/tangnano4k/pwm_top.v`。土台に `pwm_timer` と、PWM の出力のエッジを数える 1 チャネルの周波数計（0x5000）を足した。LED は PWM でも点く。
- sim（`gateware/sim/test_pwm_timer.py`、5 件、合格）: デューティーと周期、WRAPS、書き換えが周期の頭で効く、0 % と 100 %、無効にすると止まって数がクリアされる、窓の外は 0。
- 実機（`tools/p0/pwm4k/pwm_check.py`）: 周波数計の数（100 ms あたり）が 4 つの設定とも期待値ちょうど。WRAPS も、ホストの時計で 1 秒測って 0.05 % 以内。

| PERIOD / DUTY | 周波数 | エッジ / 100 ms | WRAPS / 秒 |
|---|---|---|---|
| 27 / 9 | 1 MHz | 100 000（3 回とも） | 999 501 |
| 270 / 135 | 100 kHz | 10 000 | 99 975 |
| 2700 / 2000 | 10 kHz | 1 000 | 9 999 |
| 27000 / 1350 | 1 kHz（5 %） | 100 | 1 000 |

- 最後の設定のまま残すので、LED は暗く光る（目で見る確認はユーザーに任せる）。

### 3.4 SPI フラッシュ（2026-11-05、合格）
- ピン: IDE のピンの表（`IDE/data/device/GW1NSR-4C/QFN48P.json`）で、1 = MCLK、2 = MCS_N、47 = MI、48 = MO（コンフィグ用の SPI）と確かめた [me]。調査担当の報告（CLK / CS / DO / DI）と一致する。8（JTAGSEL_N）と 9（DONE）は触らない。
- 部品は `gateware/rtl/spi_master.v`（0x8000、モード 0、SCK = 27 / 4 = 6.75 MHz）。ホストが CS# を持ったまま 1〜4 バイトずつ送受信し、フラッシュのコマンドはホストで組む。sim（`gateware/sim/test_spi_master.py`、4 件、合格）は、フラッシュと同じ向きで動く SPI のスレーブの真似と往復する。
- 回路は `spiflash_top.v` と `spiflash.cst`。`gowin_pack` の `--mspi_as_gpio` は、4K の設定にもともと入っている。
- 実機（`tools/p0/flash4k/flash_check.py`）
  - JEDEC ID `85 60 16`（PUYA、容量 2^22 バイト = 32 Mbit）。ステータスレジスタ 0x00（保護なし）。P25Q32H のデータシート V1.4 の ID の表も `85 60 16`、ステータスレジスタはビット 7〜0 が SRP0、BP4〜BP0、WEL、WIP、出荷時は 00h、WP# が固定するのはステータスレジスタだけ [agent]。
  - フラッシュは空だった: 先頭と、64 KB ごとの 64 か所の先頭 16 バイトが、すべて 0xFF。
  - 書き込みは、一番上の 4 KB の区画（0x3FF000）が全部 0xFF だと確かめてから、そこだけで行った。消去 → 256 バイトのいろいろな値を書く → 読み戻して一致 → 次のページは 0xFF のまま → もう一度消して全部 0xFF に戻した。
  - 書き込みは `--write` を付けたときだけ。保護のビットが立っているか、空いた区画が見つからなければ、何も書かずに止める。

### 3.5 PSRAM を速くする（2026-11-05、合格）
- やり方: 制御器（`hyperram_ctrl.v`）は変えず、入れるクロックを PLL で速くした。CK は制御器のクロックの 1/4 のまま。読み出しは「CK を切り替える直前に、前のエッジが出したデータを取る」作りなので、クロックを速くしても取り込みの位置関係は変わらない。
- 試験の top は `tools/p0/psram4k/hram_fast_top.v`。JTAG のブリッジ、レジスタ、`hram_burst` を全部 PLL のクロック（27 MHz × N）で動かすので、クロックをまたぐ箇所が無い。VCO は 600 MHz 以上にした（3.1）。
- `hram_burst.v` に CYCLES（1 回の取引のクロック数）を足し、`hram_burst.py` で、CS# が Low の時間とバスの速さを FPGA の中の数から出すようにした。ホストから見た「毎秒の組数」は JTAG で決まるので、速さの比較には使わない。

| 制御器のクロック | CK | 往復 | 不一致 | 書き込み | 読み出し | CS# Low の最長 | 最高周波数（配置配線後） |
|---|---|---|---|---|---|---|---|
| 27 MHz（今まで） | 6.75 MHz | 300 | 0 | 4.4 MB/s | 4.3 MB/s | 3.74 µs | 84.7 MHz |
| 54 MHz | 13.5 MHz | 300 | 0 | 8.7 MB/s | 8.6 MB/s | 1.87 µs | — |
| 81 MHz | 20.25 MHz | 300 と 1000 | 0 | 13.1 MB/s | 12.8 MB/s | 1.25 µs | 89.6 MHz |

- 速さは、8 語（16 バイト）の取引 1 回あたり。往復には、512 語の境目の直前から始まるもの 12 回を含む。
- 108 MHz は、最高周波数（89.6 MHz）を超えるので試していない。
- CS# が Low の時間が短くなった分、1 回の取引を長くすれば速さはさらに上がる（81 MHz なら 4 µs の中に約 50 語入る）。`cmd_len` は 4 ビットなので、今は試していない。
- **カメラの取り込み（camstream）は 27 MHz のまま**。あちらは `frame_ring` などを含めて 41.6 MHz が上限なので、制御器だけを速いクロックにしてクロックをまたぐ必要がある。4 番（HDMI に出す）は 1.2 MB/s で足りるので、今の速さで進める。
- **途中で見つけたこと（上流の候補）**: 54 MHz 版を `gowin_pack -c` で圧縮すると、openFPGALoader が `FsParser: checksum data is truncated` で書き込みを拒んだ。
  - 原因: Apicula の `bslib.py` は、ビットストリームで使われていないバイトの値を 3 つ選んで圧縮のキーにし、足りないと残りを 0x00 にする（`(unused_bytes + [0, 0])[0:3]`）。今回は使われていない値が 0xB5 の 1 つだけで、4 バイトと 2 バイトのキーが 0x00 になった（ヘッダーの 0x51 の行が `5100ffffffb50000`）。openFPGALoader（`fsparser.cpp`）はキーの 0x00 もそのまま使うので、データの普通の 0x00 を伸長して長さが合わなくなる。
  - 上流の master も同じコード。FPGA 本体がキー 0x00 をどう扱うかは確かめていない。
  - **調べた結果（2026-11-05）: 正しいのは Apicula の読み方で、直すべきは openFPGALoader**
    - Apicula: 0ac9be7（2025-05-15、YosysHQ/apicula#235 を閉じた変更）で、キーが足りないときは 0x00 を書いて、その段の置換をしないと決めた。読み込み側（`bslib.py`）も 0x00 のキーを「使わない」として扱う。`doc/compression.md` は「足りなければその段の圧縮をしない」とだけ書き、0x00 という値は書いていない。#235 で openFPGALoader の作者が「キーが 1〜2 個のとき Gowin がどう扱うか見たい」と書いていたが、答えは出ていなかった。
    - openFPGALoader（master）: 0x51 のキーをそのまま比べ、0x00 を特別扱いしない。伸長はチェックサムの計算にだけ使い、FPGA には圧縮のまま送る。伸長した長さが 16 ビットの倍数かを確かめる検査は、7a69d83（2026-04-10、"fsparser: check lines length"）で入った。それより前の版は拒まず、間違ったチェックサムを計算していたことになる。
    - FPGA（実機）: 2Z = 0x00 の HDMI 版（データに普通の 0x00 が 14 062 個）は正しく映った。4Z = 2Z = 0x00 のビットストリーム（`hram_fast_top` の 54 MHz 版、シード 6。普通の 0x00 が 25 026 個で偶数なので openFPGALoader が拒まない）も、PSRAM の往復 300 回が不一致 0 だった。FPGA が 0x00 を 4 / 2 バイトの 0 として読んでいたら、どの行もずれて動かない。**FPGA はキー 0x00 を使わないと読む。**
    - 注意: openFPGALoader の書き込み後の「CRC check: Success」は、FPGA の計算ではない。openFPGALoader は SRAM に書いたあと、自分で計算したチェックサムをコマンド 0x0A で usercode に書き、それを読み返して比べている（`gowin.cpp` の `writeSRAM` と `checkCRC`）。HDMI 版の usercode は 0x75e1 で、openFPGALoader の読み方の値だった（Apicula の読み方なら 0xb5d0）。
    - Gowin の資料（TN653、UG290）は取得できず、ベンダーのツールが足りないキーに何を書くかは確かめていない。
    - 直し方の案: openFPGALoader の `fsparser.cpp` で、0x00 のキーは比べない（例: キーが 0 なら伸長の表に入れない）。
  - 対処: `hram_burst.py` だけ `-c` を外した。4K のビルドの設定（`boards.yaml`）の `-c` は、同梱のビットストリームが変わるので触っていない。ほかのデザインでも、空いたバイトの値が 3 つ未満になると同じことが起きうる。

### 3.6 カメラ → PSRAM → HDMI（2026-11-05、合格）
**設計**（作る前に書いた）
- 新しいオーバーレイ `camhdmi`。camstream（ホストへの取り込み）は変えない。
- カメラ（160×120 のグレー）を、PSRAM の 3 面のフレームバッファーに書く。HDMI は 640×480@60 で、1 画素を 4×4 に広げて出す。
- 帯域: 表示は 1 ラインを 4 回使うので、PSRAM から読むのは 160 バイト / 4 ライン（約 1.2 MB/s）。カメラの書き込みは平均 0.2 MB/s。今の制御器（27 MHz、CK 6.75 MHz、8 語で 4.3 MB/s）で足りる。
- `gateware/rtl/cam_fb.v`（clk 側、レジスタも持つ）
  - カメラ側: PCLK 側で残すバイトを 1 ライン（160）ずつ BSRAM の片側に詰め、トグルで clk 側に渡す。clk 側は 8 語 × 10 回で PSRAM に書く。ラインの区切りはバイト数で決める（HREF には頼らない）。
  - 1 フレームが 19 200 バイトでなければ捨てて BAD に数える。
  - 書く面は「最後に書き終えた面」でも「表示中の面」でもないものを、ライン 0 のときに選ぶ（裂けない）。書き終えた面は、最後のラインの最後の書き込みが終わってから切り替える。
  - 表示側からのライン要求（トグル）で、表示中の面からその 1 ラインを 8 語 × 10 回で読み、表示のラインバッファーに書く。ライン 0 の要求のときに、表示する面を「最後に書き終えた面」に切り替える。
  - 書きと読みは、1 ライン（10 回の取引）ずつ交互に制御器を使う。表示の要求を先にする。取引は 8 の倍数の語から始まるので、512 語の境目をまたがない。
- `gateware/rtl/fb_display.v`（pclk 側）: `video_timing` と、2 ライン分のラインバッファー（BSRAM、clk 側が書き、pclk 側が読む）、TMDS の符号化器 3 つ。

- レジスタ（0x6000）: CTRL（書き込みの有効）、FRAMES（書き終えたカメラのフレーム）、BAD（捨てたフレーム）、HFRAMES（HDMI のフレーム）、STATUS（面の番号）。

### 3.7 カメラの絵を大きくする（320×240 を 2 倍で 640×480）
**設計**（作る前に書いた。ユーザーと合意済み、2026-11-05）
- camhdmi を 320×240 のグレーにして、1 画素を 2×2 に広げて 640×480@60 に出す。camstream は変えない。160×120 版は残さない（パラメーターを戻せば作れる）。
- 帯域: 表示は 2 ラインごとに 320 バイト（約 5.0 MB/s）、カメラの書き込みは 76 800 バイト × 毎秒約 8 枚（約 0.6 MB/s）。27 MHz の制御器（4.3 MB/s）では足りない。
- **クロック**: HDMI 用の PLL とは別の、2 つ目の PLLVR で 81 MHz（VCO 648 MHz）を作り、`hyperram_ctrl` と `cam_fb` をそのクロックで動かす（CK 20.25 MHz、3.5 で不一致 0 だった速さ）。Apicula のチップの情報には PLLVR が 2 つあるが（`chipdb.py` の pll_idx 0 / 1）、2 つ同時に使ったビルドはまだ無い。
  - 2 つ目の PLL が通らないときの代わり: HDMI 用の PLL の CLKOUTD（126 / 2 = 63 MHz）。その場合は余裕が足りないので、ラインバッファーを 4 ライン分にして 2 ライン先から読む。
- 最悪の待ち: 表示の要求は次のソースのラインを 2 表示ライン（63.5 µs）前に出す。81 MHz では 1 ライン（16 バイトの取引 20 回）が約 24.4 µs なので、書き込み 1 ラインの直後でも約 49 µs で間に合う。
- **クロックをまたぐ箇所**
  - JTAG のブリッジ、`base_regs`、I2C、DVP は 27 MHz のまま（DVP の XCLK は clk / 2 で決まる）。
  - 27 MHz のバスと `cam_fb` のレジスタの間に、新しい `gateware/rtl/bus_cdc.v` を置く: 27 MHz 側でアドレスの範囲から hit を出し、トグルで 81 MHz 側に 1 回のバスの取引を起こし、ack とデータをトグルで返す。アドレスとデータは、トグルが渡る間は止まっている（ブリッジは ack まで stb を保持する）。往復は 27 MHz で 10 クロック前後で、ブリッジが求める「次のスキャンの前」（TCK の数周期）に収まる。
  - `cam_fb` とカメラ（PCLK）、`fb_display`（画素のクロック）の間は、今と同じトグルと BSRAM の両側のクロック。
- **`cam_fb.v`**: W（16 の倍数で 512 以下）と H（255 以下）を広げられるようにする。カメラ側の BSRAM と表示のラインバッファーは 2 × 128 語（`lb_addr` を 8 ビットに）、ライン番号と `req_line` は 8 ビット、取引の番号 `k` は 5 ビット、バイト数は 17 ビット。STRIDE は 65 536 語（1 フレーム 38 400 語）。1 ラインは 160 語で 8 の倍数なので、取引は 512 語の境目をまたがない。
- **`fb_display.v`**: 拡大率をパラメーター SH（2^SH 倍、1 か 2）にする。表示のライン y が 2^SH の倍数のときに次のソースのラインを要求し、v = 520 でライン 0 を要求するのは今と同じ。
- レジスタ（0x6000）は今と同じ。マニフェストの width / height を 320 / 240 にする。
- 合格の条件はチェックリストの 7 のとおり。PSRAM の往復は 3.5 の 81 MHz の結果を使わず、このビルドの日に `hram_burst.py --mult 3` で取り直す。

- クロックの実測（捨てる top に `clk_meter` を足した、シード 2）: 2 つ目の PLL が 81.0000 MHz、画素のクロック 25.2000 MHz、HDMI の PLL 126.0000 MHz。どちらの PLL も LOCK が 1。

**途中で見つけたこと: 遅れて ack する slave は、このバスにそのままはつなげない**
- 最初のビルドでは、`cam_fb` のレジスタへの書き込みは効く（CTRL を 0 にすると絵が止まり、1 で動く）のに、読み出しはどれも 0 だった（done のビットは 1）。
- 原因: このバスの slave（`base_regs` の中のもの、`i2c_master`、`dvp_frontend` など）は、hit に関係なくすべての stb に 1 クロックで ack し、データだけを hit で 0 にする作り。ブリッジは最初の ack で取引を終える。`bus_cdc` の ack は数クロック遅れるので、ほかの slave の ack（データ 0）が先に取られていた。書き込みは `bus_cdc` が stb の時点で取り込むので効いていた。
- 切り分け: RTL の sim と、合成後のネットリストの sim（`bus_cdc` + `cam_fb`）はどちらも正しく読めた。スキャンの間に TCK を 140 回空けても 0 のまま（ブリッジの時間の問題ではない）。`bus_cdc` に定数を返させても 0 だった（`cam_fb` の問題ではない）。
- 直し方: `camhdmi_top.v` で、`bus_cdc` の hit の間はほかの slave に stb を見せない（`stb & !fb_hit`）。共通の部品は変えていない。直した後、読み出しが正しく返り、上の確認に合格した。

**まだ分からないこと**
- クロックを測るために作った捨てる top のうち、`clk_meter` で画素のクロックと 81 MHz を測ったもの（シード 1）では、画素のクロックが数えられず、HFRAMES も 0 だった。HDMI の側が動いていない。書き込み直しても同じだった。測る対象に 126 MHz を足したもの（シード 2）は正しく動いた。配置によって HDMI の側のクロックが動かなくなることがあるらしい。
  - 配置を比べた: PLL はどのビルドでも同じセル（HDMI 用 X27Y0、81 MHz 用 X36Y0）。違うのは CLKDIV（/5）で、動かなかったものは下端の `X17Y19/CLKDIV_HCLK1_SECT1`、動いたものは上端（シード 2 の測定用 `X18Y0/CLKDIV_HCLK1_SECT0`、本体の camhdmi `X18Y0/CLKDIV_HCLK0_SECT1`）。
  - 仮説: 下端の CLKDIV は、Apicula の扱いか配線のどこかで動かない。確かめるには、CLKDIV を下端に固定したビルドで再現するかを見る。本体の camhdmi（シード 1、ハッシュ `85904b3f…`）は上端に置かれていて、動いている。
- 作り直した camstream の実機の確認はしていない（camstream の回路は変えていない）。

**回帰**
- 4K の土台を作り直すと、同梱のものと同じハッシュ（`89b57016…`）。
- `uv run pytest -q`: 189 件合格。`uv run pytest -m sim -q`: 15 本合格（足した bus_cdc と、cam_fb の 2 つ目のビルドを含む）。

### 3.8 ユーザーフラッシュの読み出し（2026-11-06、実機の前で中断）
**設計**（作る前に書いた。ユーザーと合意済み、2026-11-06）
- `gateware/rtl/uflash_reader.v`: 32 KB を 0x10000〜0x17FFC にそのまま割り当てる。語の番号 w = adr[14:2] とし、XADR = w[12:6]、YADR = w[5:0]（EMPU と同じ分け方。M3 のバイトアドレスは 4w）。
- 読み出しの流れ（27 MHz）: アドレスと XE = YE = 1 → 次のクロックで SE = 1 → 次で SE = 0 → SE が上がってから 2 クロック後に DOUT を取って ack、XE / YE を下げる。書き込みは ack だけ返して何もしない。PROG / ERASE / NVSTR / DIN は回路の中で 0 につなぐ。
- ack が 4 クロック遅れるので、top でほかの slave には `stb & !hit` を見せる（3.7 と同じ）。

**資料で確かめたタイミング**（UG295-1.4.4E [me]）
- FLASH256K のタイミングは FLASH64KZ と同じ（3.4 節）。表 3-9 と図 3-7: Tacc は SE の立ち上がりから最大 25 ns。SE の High は 5 ns 以上（Tpws）、Low は 2 ns 以上（Tnws）。アドレスと XE / YE は、SE の立ち上がりから 25 ns 以上保つ（Tah）。
- 表 3-13: 読み出しは XE = YE = SE = H、PROG = ERASE = NVSTR = L。3 本とも High で働く（表 3-12）。
- **表 3-1 の注: 「The User Flash of GW1NS-4C, GW1NSR-4C, and GW1NSER-4C is provided for MCU.」**

**sim**（`gateware/sim/test_uflash_reader.py`、2 件、合格）
- フラッシュは、自分で書いた読み出しのモデル `gateware/sim/flash256k_model.v`（Gowin の `prim_sim.v` はライセンスの都合で使わない）。DOUT は SE が上がってから 24 ns は X。手順の違反を数える: PROG / ERASE / NVSTR が 0 でない、XE と YE なしで SE が上がる、SE が上がってから 25 ns 以内にアドレスか XE / YE が変わる。
- X / Y の境目（0、63、64、4095、4096、8191）と乱数の 40 語が正しく読める。ack は 4 クロック。ack の後のデータは 0。書き込みは 1 クロックで ack し、フラッシュに触らない。範囲の外は hit も ack も出さない。違反は 0。
- 注意: 取り込みを 1 クロック早めた変異は、X のためではなく、別の検査（ack の後のデータが 0）で落ちた。モデルの 24 ns が 1 クロック（37 ns）より短いため。X の検査は、SE と同じクロックで取り込む誤りしか捕まえない。

**ビルド**（シード 1、ハッシュ `839d25d9…`）
- 通った。FLASH256K は `X0Y0/USERFLASH` に置かれた。27 MHz の側の最高周波数は 106 MHz。
- **配置配線の後の json で、FLASH256K のすべての入力（PROG / ERASE / NVSTR / DIN を含む）と DOUT に、INIT 0x5555（NOT）の LUT が入っていた。** PROG / ERASE / NVSTR は「GND → NOT → FLASH256K」。nextpnr の `pack_userflash` は、EMCU が無いときすべてのピンに反転を入れる（FLASH96K / FLASH608K の 1K / 9K と同じ扱い）。
- ビットストリームを `gowin_unpack` で戻して確かめた。PROG（`R1C1_A3`）、ERASE（`R1C1_C6`）、NVSTR（`R1C1_C7`）は、それぞれ INIT 0x5555 の LUT から来ていて、その LUT の入力は VSS。**実際の配線には 1 が入る。**

**Gowin の IDE との比べ**（V1.9.11.03 Education、GW1NSR-LV4CQN48PC6/I5）
- M3 なしで FLASH256K を置いた小さな top: `ERROR (PA2090) : 'FLASH256K'(f) must be used with 'EMCU' for current device` で止まった。
- EMCU を使う上流の例（Apicula の `examples/emcu-blinky.v`。Makefile に tangnano4k の目標がある）は IDE でビルドできた。その中で FLASH256K の PROG / ERASE / NVSTR は GND につながっている。IDE のビットストリームを `gowin_unpack` で戻すと、`R1C1_A3` / `R1C1_C6` / `R1C1_C7` はどれも `R1C2_W21` を通って **VSS（0）** だった。
- nextpnr も、EMCU があるときは反転を入れない。Apicula は EMCU と FLASH256K のどちらにもヒューズを出さないので、EMCU があってもなくても同じ配線を使う。
- **結論: このチップでは、FLASH256K のピンの配線は UG295 のとおりの向き（反転なし）。M3 なしのとき nextpnr が入れる反転は誤りで、PROG / ERASE / NVSTR に書き込みと消去を指示する 1 を入れ続ける。** このビットストリームは実機に書き込んでいない。
- `emcu-blinky` は、XE / YE をリセットの入力から直接（反転なしで）入れている。Apicula の `doc/emcu.md` によると、M3 の flash ポートの RDATA は、フラッシュの DOUT にハードウェアで直結している。なので、M3 なしでファブリックから DOUT を読めるかは、反転とは別に分からない。

- 原因: `schtasks /run` はタスクを起動するとすぐ戻る。そのあと `usb_recover.py` が毎秒デバイスを開いて応答を見ていたため、pnputil が再起動しようとした時点でハンドルが開いていた。
- 修正: タスクの実行が終わるまで待ってから応答を見る。pyusb のポートのリセットのあと、ハンドルを明示的に解放する。テストは `tests/test_usb_recover.py`。
- 修正後の確認: 応答しているボードで `--force` を付けて流した。イベント 225 は出ず、デバイスがつなぎ直され（LastArrivalDate 10:45:42）、そのあとも応答した。

**ポート**
- 固まったときは、マザーボードの AMD の USB 3.x コントローラーのポート（Port_#0002.Hub_#0001）に直接挿していた。
- 2 回目の抜き差しで、別のポート（Port_#0001.Hub_#0001）に挿し替えた。そのあと、書き込み、ER1 の読み書き、USB の再起動は問題なく通った。
- ポートが原因かどうかは、まだ分からない（固まったのは 2 回だけ）。また固まるかどうかを見ていく。
