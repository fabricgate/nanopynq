# Tang Nano 20K の SDRAM を実機で確かめた（2026-11-16）

## 結論
- **8 MB の SDRAM は、自己試験とホストからの読み書きの両方で誤りなく動いた。** 確認は `tools/p0/sdram20k/hw_check.py`（5 手順）で、全部 PASS。
- RD_LAT（読み出しの遅れ）は 0〜5 を試し、**2〜5 が誤り 0**。既定の 2 は範囲に入っているので、既定は変えていない。ただし 2 は範囲の下の端。既定の 2 はデータシートの有効窓に合わせた値で、3〜5 が通ったのは保証された余裕ではない（1.1 を参照）。
- 8 MB の自己試験 1 回は 0.72 s（10 回とも同じ）。ホストの読み書きは約 16 000 語/s。
- 自己試験を動かしている最中にホストが別の領域を読み書きしても、両方とも誤りなし。
- 圧縮（`-c`）の .fs を openFPGALoader が拒否する原因は、**Apicula が「鍵なし」を 0 で表し、openFPGALoader v1.2.0 が 0 を鍵として扱う食い違い**（4 節）。今の SDRAM 設計は `-c` を付けても Apicula が非圧縮に戻すので、今回は問題にならない。

## 1. 結果
ボードは Tang Nano 20K、ビットストリームは同梱の `tangnano20k-sdram`（SRAM のみに書き込み、フラッシュには触れていない）。

### 1.1 RD_LAT を振る（8 MB 全体を 1 回ずつ）
| RD_LAT | 誤り | 最初の誤り |
|---|---|---|
| 0 | 2 097 152（全語） | 0 番地、読み 2548598351、期待 0 |
| 1 | 2 097 152（全語） | 0 番地、読み 4294967295、期待 2246822507 |
| 2（既定） | 0 | なし |
| 3 | 0 | なし |
| 4 | 0 | なし |
| 5 | 0 | なし |

- 取り込みが早すぎる 0 と 1 は全語が外れ、2 以上は全部通る。上の端（6、7）は試していない。
- 既定を 2 のままにした理由: 2 は、モデルのデータシートの窓（Read コマンドのエッジから約 61.6〜95.1 ns）の中（74 ns）で取り込む。3〜5 が通るのは、駆動されていない DQ 線が直前の値を保っている（バスの電荷）せいと考えられ、データシートは保証しない。失敗の境目が Read エッジの 37〜74 ns 後のどこかにあることしか分からない（RD_LAT=2 の早い側の余裕は測っていない。sdram_clk（clk の反転）は一般配線を通る）。駆動されていない DQ が値を保つ根拠: RD_LAT=0 の最初の誤りの読み値 2548598351 は、書き込み段階で最後に書いた語 (2^21−1)·K1 mod 2^32（K1 = 0x9E3779B1）と一致する。RD_LAT=1 が 0xFFFFFFFF を読む理由は説明できていない。2 で失敗するボードが出たら、再ビルドせずに `ol.sdram_test.rd_lat = 3` で変えられる。
- 試作の別コントローラー（nestang）は 3 クロック後の取り込みで通っていた。これが上の電荷の説明と合うかは確かめていない。

### 1.2 自己試験 10 回（8 MB 全体、RD_LAT=2）
10 回とも ERRORS=0、1 回 0.72 s。

### 1.3 わざと誤りを入れる
PASSES=3、START=0x1000、LENGTH=0x10000 で ERRORS=3。FIRST_ERR は 0x9000（= START + LENGTH/2）。読み 2987211087、期待 1307756208。

### 1.4 ホストからランダムな 10 000 語
8 MB 全体の重複しないランダムな語位置 10 000 か所（seed 固定）へ 1 語ずつ書いて読み戻し、不一致 0。書き 3 473 語/s、読み 3 719 語/s（1 語ずつ）。連続の読み書きは約 16 000 語/s（以前の実行）。

### 1.5 同時に使う
前半 4 MB で自己試験（PASSES=20）を始め、動いている間に後半 4 MB へランダムな 2000 語を書いて読んだ。ホストが終わった時点でも試験は動いていた。試験は 20 回終了、ERRORS=0。ホストは一致（書き 16 105、読み 16 355 語/s）。

- 先に測った 14 700 語/s（読み）に対し、今回は約 16 000 語/s。測り方の違い（語数、連続か）の範囲と思われるが、原因は調べていない。

## 4. 圧縮した .fs を openFPGALoader が拒否する原因（2026-11-16）
### 4.1 結論
- 原因は、圧縮の「鍵」の 0 の扱いが両者で違うこと。Apicula は、使われていないバイト値が足りないとき、足りない鍵を 0 のままにして「その圧縮は使わない」とみなし、0x00 のバイトをそのまま書く。openFPGALoader v1.2.0 は 0x51 行の 3 つの鍵（8 個・4 個・2 個の 0x00 の代わり）をそのまま比べるので、鍵が 0 だと、書かれている 0x00 のバイトを全部「0 が 4 個（または 2 個）」に伸ばす。その結果、伸ばしたあとのビット数が 16 の倍数でなくなり、`checksum data is truncated` になる。
- どちらの不具合かは、規格書（Gowin の bitstream の仕様）を見ていないので断定できない。openFPGALoader 側は 0 を「鍵なし」として扱えば直る（下の確認）。Apicula 側は 0 を鍵に使わない書き方にはできない場合がある（使われていない値が 1〜2 個しかない設計）。実機（チップ）が鍵 0 の圧縮ファイルを受け付けるかは確かめていない。
- 上流への報告・コメントはしていない（ユーザーが決める）。

### 4.2 見たもの
- openFPGALoader v1.2.0 `src/fsparser.cpp`（`FsParser::parse()`）。0x10 行の bit 13 で圧縮かどうか、0x51 行で `_8Zero`、`_4Zero`、`_2Zero` を読む。圧縮のときは各行のデータを 1 バイトずつ見て、`c == _8Zero`（64 ビット）、`c == _4Zero`（32 ビット）、`c == _2Zero`（16 ビット）の順に調べ、当たらなければそのバイト（8 ビット）。鍵が 0 かどうかの判定はない。全部つなげたビット数が 16 で割り切れないと `checksum data is truncated`（329 行付近）。
- Apicula `bslib.py` の `write_bitstream` と `compressLine`。使われていないバイト値を小さい順に 3 つ取り（8 個・4 個・2 個用）、足りない分は `(unused_bytes + [0, 0])[0:3]` で 0 を入れる。`compressLine` は鍵が 0 の圧縮をしないので、0x00 のバイトは書き換えずに残る。1 つも使われていない値がなければ、圧縮せずに書く（`No unused bytes, will be uncompressed.` を表示）。
- Apicula 自身の読み込み側（`read_bitstream`）は `if ba[6]:` のように鍵が 0 なら無視する。つまり Apicula は 0 を「鍵なし」と決めている。
- 失敗するファイル: 以前の SDRAM 試作（`~/tools/gw2a18c-jtag/sdram-spike/out1/top.fs`、リポジトリ外）。0x51 行の鍵が 171, 0, 0 で、使われていないバイト値が 171 の 1 つだけの設計だった。`openFPGALoader.exe -b tangnano20k --verbose` で `FsParser: checksum data is truncated` と `can't parse file` を再現した（パースだけで止まり、書き込みはしていない）。
- `tools/p0/sdram20k/fsparse_port.py`: FsParser のチェックサムの手順を Python に写したもの（ビット数を数えるだけ）。結果は次のとおり。

| ファイル | 鍵 8/4/2 | 伸ばしたビット数 mod 16 | 結果 |
|---|---|---|---|
| sdram-spike/out1/top.fs（圧縮） | 171 / 0 / 0 | 8 | truncated（0x00 のバイト 58 689 個が 32 ビットに伸びる） |
| 同じファイルで、0 の鍵を無視（`fix` 引数） | 同上 | 0（4 552 064 ビット） | OK |
| sdram-spike/out1/top_nc.fs（非圧縮） | － | 0 | OK |
| base20k/seed2/base.fs（圧縮） | 106 / 107 / 149 | 0（4 552 064 ビット） | OK |

0 の鍵を無視して伸ばしたビット数（4 552 064）は、正常に読める圧縮ファイル（base20k）と同じ。この点からも、展開後のビット数が一致する。

### 4.3 この設計は何が違うか
- 20K のベース設計の鍵は 3 つとも 0 でない値（使われていないバイト値が 3 つ以上ある）なので読める。SDRAM 設計はビットストリームが詰まっていて、使われていないバイト値が少ない。試作は 1 つ、今の `sdram_top.v` は 0 個（シード 1〜5 で、`-c` を付けるといずれも `No unused bytes, will be uncompressed.`）。
- 今の設計を `-c` で pack したファイルは、同梱の非圧縮の `base.fs` と改行を除いて一致し、openFPGALoader で SRAM に読み込めた（`-b tangnano20k`、SRAM のみ）。よって今は `-c` を付けても動く。`tools/build_base.py` の `NO_COMPRESS` は、鍵が 1〜2 個だけ足りない設計になったときの用心として、そのままにしてよい。
- 同じ形（鍵が 181, 0, 0）の圧縮ファイルが、Tang Nano 4K のカメラの試作ビルドにもある。openFPGALoader での読み込みは試していない。

### 4.4 確認できなかったこと
- 実機が鍵 0 の圧縮ファイルを受け付けるか（openFPGALoader が拒否するので、他の書き込みツールを使わないと試せない）。Gowin の仕様書は見ていない。
- openFPGALoader の最新版（v1.2.0 より後）で直っているか。
- 4K のカメラの試作が同じ原因で拒否されるか（上記のとおり未実行）。
- 失敗した試作の `out1/top.fs` は、リポジトリ外にある 1 回限りのビルド。同じ設計をもう一度ビルドしても再現するとは限らない（今の RTL では非圧縮に戻る）。

## 5. main への rebase と `.npq` での作り直し（2026-11-19）
- main（`.npq`、sysinfo 1.1、共通の回路の置き場所が `src/nanopynq/rtl`）に rebase した。`sdram_*.v` は `src/nanopynq/rtl/` に移り、`tools/build_base.py` の `sdram` には読み込むソースを順番どおりに書いた。`sdram_top.v` は、ほかの top と同じく `DESIGN_ID` を sysinfo に渡す。
- 同梱の `tangnano20k-sdram` を `base.npq` と `build.json` で作り直した（`--seed 1`、oss-cad-suite 2026-11-15、Apicula da0e33e、`-c` なし）。`.fs` の sha256 は `76e112f6…`、識別値は `0x1ef753ef`。
- 実機（Windows）: `Overlay("sdram", board="tangnano20k")` で、版 `0x10001`、識別値がファイルと一致した。続けて `hw_check.py --no-download` の 5 手順がすべて PASS（RD_LAT 0/1 は誤り、2〜5 は 0 件、既定 2。8 MB の自己試験 10 回は誤り 0 で各 0.72 s。誤りの注入は 0x9000 で検出。ランダムな 10 000 語は不一致 0（書き 3281、読み 3364 語/秒）。同時使用は誤り 0、ホストの読み書きは約 15 400 語/秒）。1 章と同じ結果。
- nextpnr の `Failed to route net 'arb.clk' … using dedicated routing.` の警告は、rebase の前の版（同梱の `.fs` と同じ sha256 `5bceca18…` が再現した）でも出ている。前からあるもので、実機の結果にも影響していない。
