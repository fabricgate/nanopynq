# Tang Nano 4K のカメラの連続取り込み（PSRAM のリング）の受け入れ（設計書 4.14）2026-11-04

## 結論
- ノートブックで `Overlay("camstream", board="tangnano4k")` を開き、`Camera(ol.cam_i2c, None, ol.cam_dvp, ring=ol.cam_ring)` を組み立てると、`cam.stream(20)` で 160×120 のグレーのフレームを 20 枚続けて受け取れた。毎秒 2.25〜2.38 枚、DROPPED 0、壊れた枚数 0。
- `cam.record(50)` は、センサーの速さ（毎秒約 8.4〜8.7 枚）で 50 枚を PSRAM に溜めてから読み、通し番号 0〜49 に飛びが無かった。リングを 5 秒動かすと、センサーの VSYNC 42 回に対して書けたフレームが 41 枚（境目の 1 枚の差）で、捨てたフレームは 0。
- リングが満杯になると、新しいフレームは捨てて DROPPED に数え、ホストが読んでいる区画は上書きしない。実機で 33 秒動かしたとき、センサーの 278 枚 = 書けた 256 枚 + 捨てた 22 枚で、読み終えて空いた区画 0〜2 に次の 3 枚（通し番号 256〜258）が正しく入った。
- 土台（4K と 9K）とカメラ用のオーバーレイの回帰は無い。負荷試験は 3 つのデザインで各 500 回、不一致 0。既存のテスト 186 件と sim 5 本が通る。
- 最後のレビューで 2 つの不具合が見つかり、直した（3 章）。フレームの途中で `reset()` すると、前の回の区画 0 が新しい回の通し番号 0 として渡ること（ノートブックの順番どおり `stream()` の直後に `record()` を呼ぶと起きる）と、PSRAM の読み出しが時間切れになっても知らせないこと。
- ハブの仕様に `streams` の `register` と `framing` を足す件は未定（ユーザーの判断）。同梱のマニフェストには `register: window`、`framing: slot-header32` を書いてあり、nanopynq は `dir` と `mtu` だけを確かめる。

## 2. 実機の結果（Tang Nano 4K、Windows 11）
### 2.1 PCLK とライン数（計画 Task 1 の判定）
- 毎秒 8.667 フレーム、PCLKS 297603、LINES 120（何度読んでも同じ）。
- PCLK の周波数 ≈ PCLKS × フレーム数/秒 ÷（VSYNC がフレームの水準にある割合）。割合を 1.0 とすると 2.58 MHz、0.9 とすると 2.87 MHz。
- 1 行の周期（ブランキングを含む）は 0.87〜0.96 ms。残すバイト（行あたり 160）の平均の速さは 0.17〜0.19 MB/s で、止まる条件（3 MB/s）より十分小さい。行の中（HREF の間）でも約 1.4 MB/s で、PSRAM の書き込み（8 語の取引で約 4.5 MB/s）より遅い。

### 2.2 制御器の往復（`tools/p0/psram4k/hram_burst.py`）
- 8 語のバーストを 300 回、ランダムな値で書いて読み戻し、不一致 0 件。そのうち 12 回は 512 語の境目をまたぐアドレス（PSRAM の行の境目の候補）から始めた。毎秒 231 組（書きと読み）。
- 配置は `hram_probe.py` の確認（IO 17 本、上端の行は clk と led だけ）を通った。

### 2.3 オーバーレイのビルド
- 2 回作って同じハッシュ（レビューの修正の後で `48be43c9…`）。BSRAM 2/10、PLL 0、LUT4 1889/4608、DFF 1272/3456、ALU 862/3456。clk の最大周波数 41.6 MHz（使うのは 27 MHz）、PCLK 側 47.0 MHz。タイミング違反なし。
- 配置の確認: IO 31 本、HyperRAM の 13 本が P0 の表の位置（行 19）、上端の行は camera.cst のピン（clk、led、SCL、SDA、VSYNC、HREF、PCLK、D6、D7）だけ。

## 3. 途中で分かったこと
- **フレームの途中の reset（最後のレビューで発見）**: `enable(False)` の後も、受け付けたフレームは最後まで書かれる。その途中で CTRL[1] が来ると WSEQ が 0 に戻ったあと、そのフレームの見出しの書き込みで WSEQ が 1 になる。ホストは区画 0 を読み、前の回の通し番号 0 の見出しが残っているので、古いフレームを新しいフレームとして受け取った。`stream()` の後に `record()` を呼ぶと起きる。CTRL[1] で、書いている途中のフレームに「捨てる」印を付け、データの残りは読み捨て、見出しを書かず、WSEQ も進めないように直した。sim でデータを書いている途中と見出しを書いている途中の両方を試し（直す前は失敗）、実機で `stream()` → `record()` を 2 回繰り返して確かめた。
- **読み出しの時間切れ（最後のレビューで発見）**: 制御器は RWDS が来ない読み出しを 26 CK で打ち切るが、それをリングに知らせていなかった。窓の中身がずれても、ホストは正しいデータとして読んだ。4 語に足りない読み出しがあれば STATUS[2] を立て（次の FETCH で下ろす）、ドライバは例外にするようにした。sim の HyperRAM の真似で 1 回だけ RWDS を返さない場合を試した。
- **FIFO の満杯の判定の幅**: `(wp - rp_w) == FD` は Verilog では 32 ビットで計算されるので、ポインタが一周すると満杯を見逃し、FIFO を上書きした。差を FIFO のポインタと同じ幅の wire に入れて直した。sim のあふれの試験を「3 枚とも壊れた印」に強め、直す前は失敗することを確かめた。
- **BSRAM の種類**: yosys は、2 つのクロックで使う 16 ビット幅の RAM を DPX9B（真の 2 ポート）に、32 ビット幅のものを SDPX9B に割り当てる。この基板で実績があるのは `capture` の SDPX9B なので、書き込みの FIFO は 32 ビット × 512 にした。フレームの最後の 4 バイトは半端になり得るので、clk 側はフレームの終わりを見るまで、一番新しい項目に手を付けない。
- **IO のセルの名前**: 配置の後の IO のセルの名前は、ポートの名前と一致しない（DQ と RWDS は `hpram` を含まない）。配置の確認は位置（BEL）で行う。
- **使わないモジュールでもビットストリームが変わる**: `gateware/rtl/` に `hyperram_ctrl.v` と `frame_ring.v` を足すと、それを使わないカメラ用のオーバーレイのハッシュが変わった（同じソースなら毎回同じ）。土台（4K と 9K）は変わらなかった。カメラ用のオーバーレイは今のソースで作り直して同梱し、実機で 20 枚と負荷試験を確かめた。
- **2 枚ずつ似た明るさ**: `stream()` の最初の 20 枚は、明るさの平均が 2 枚ずつ同じ値になった（自動露出が落ち着くまでの間）。中身は毎回違うので、リングの問題ではない。

## 4. 決めたこと（計画からの変更。台帳に理由と、違ったときの代価を残した）
- 制御器の sim は `hyperram_ctrl` そのものを toplevel にした（計画の `sim_ring_top.v` はリングの試験だけに使う）。
- 読み出しはモデルのレイテンシ 14 で 8 語だと 25 CK サイクルになるので、リングの先読みは 4 語ずつ（21 CK）。書き込みは 8 語で 24 CK。どの取引も CS# が Low の時間は 4 µs 未満。
- フレームの区切りは、PCLK 側がフレームの終わりに「入れた語数・バイト数・あふれ」を保持してトグルで渡す形にした。clk 側がそのフレームを終える（ack が戻る）前に始まったフレームは取らず、DROPPED に数える（カメラの速さでは起きない）。
- 計画の sim の試験 5 件に、区画より大きいフレーム、21 バイトと 15 バイトのフレームの 3 件と、レビューの修正の回帰の 3 件を足した。配置の確認の単体テスト（`tests/test_build_placement.py`）も足した。
- `SLOT_INFO` は `[15:0]` 区画の語数、`[31:16]` 区画の数。窓の 32 ビットの語 i は区画のバイト 4i〜4i+3（`capture` と同じ並び）。
- ホストは、見出しの通し番号の下位 15 ビットが RSEQ と合わないフレームも壊れたものとして扱う。`stream()` と `record()` は、壊れた印が無いのに大きさが違うフレームで `RuntimeError`（`snapshot()` と同じ）。
- IP の説明には常に `streams` を入れる（無ければ空）。`dir` は `read` と `write` だけを受け付ける（ハブの仕様の原文は手元に無い）。

## 5. 確かめられなかったこと
- **書き込みの FIFO のあふれ、区画より大きいフレーム、読み出しの時間切れ**は sim でだけ確かめた。実機の QQVGA のグレーでは、行の中でも PSRAM の書き込みのほうが速く、起こせない。
- 高い温度での tCSM（1 µs、125 ℃）。今の取引は最長 3.6 µs で、4 µs（85 ℃）の範囲だけを見ている。
- PSRAM の実際の読み出しのレイテンシ。読み出しは RWDS で取るので動きには関係しないが、sim のモデルの 14 は P0 からの推定。
- QVGA 以上の大きさ、カラー（RGB565、YUV の色差）、JPEG。区画は 32 KB なので、QVGA のグレー（76.8 kB）は入らない。
- Linux、9K（`frame_ring` は 4K の PSRAM 専用）。
- ハブの仕様に `register` と `framing` を足すかどうか（ユーザーの判断）。
