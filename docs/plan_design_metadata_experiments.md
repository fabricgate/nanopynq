# メタ情報ファイルと識別値の実験計画 2026-11-18

仕様の案(`docs/spec_design_metadata.md`、issue #24)を、実装と実機で確かめるための計画。実験の結果で仕様を直す。

## 結論と要約

- **実験は 9 つ。うち 6 つは実機なしで進められる(A 群)。残り 3 つは Tang Nano 9K か 4K が要る(B 群)。** A4、A5、A6 は、A1 の結果を受けて 2026-11-18 に足した。
- **A 群を先に行う。** 識別値の計算が Python とブラウザで一致すること、sysinfo 1.1 が回路に収まること、いまのデザインを新形式で読めることを、実機なしで確かめる。
- **実験のコードは、実験ごとのブランチに置く。** 仕様の文書に入れるのは結果だけ。実験で仕様を変えたら、仕様の該当の章を書き換え、この資料の記録の表に残す。
- **どの実験も、やめる条件を先に決めてある。** 条件に当たったら、実装を続けずに仕様へ戻る。

## 1. 進め方

- 1 つの実験は 1 つのブランチ(`exp/24-<番号>-<短い名前>`)で行う。仕様のブランチ(`docs/24-design-metadata-spec`)から切る。
- 実験のコードは、そのまま本実装にしない。通った実験の中身を、あらためて実装の issue に分ける(仕様の 9 章)。
- 実機に書き込むのは SRAM だけにする(電源を切れば元に戻る)。フラッシュには書かない。
- 結果は、この資料の 4 章の表に 1 行で残す。数字(LUT の数、往復時間、計算した値)は、測ったものをそのまま書く。

## 2. A 群: 実機なしで行う実験

### A1. 識別値を Python とブラウザの両方で計算する

- **確かめたいこと**: 仕様 5.4 の手順で、Python の実装と JavaScript の実装が同じ値を出すか。
- **仕様の章**: 5.4
- **手順**:
  1. Python で、`ips` から識別値を計算する関数を書く。仕様の計算例(`tangnano9k-base` が `0xabf78d8c`、`tangnano4k-camstream` が `0xca950154`、`tangnano4k-base` が `0x79d574b7`)をテストにする。
  2. JavaScript で同じ関数を書く(ブラウザの `crypto.subtle.digest` を使う。Node でも動く)。
  3. 同梱の 5 件すべてと、わざと作った難しい入力で、2 つの結果を比べる。難しい入力: キーの順序が逆のもの、`doc` が深い階層にあるもの、ASCII 以外の文字を含むパラメータ、`0x` の大文字と小文字、`addr_range` を省いたもの、大きな整数(2 の 53 乗の近く)。
- **通ったと言える条件**: すべての入力で 2 つの値が一致し、仕様の計算例とも一致する。
- **やめる条件**: キーの並べ方か整数の扱いで、2 つの実装を一致させるのに仕様に書いていない決まりが 3 つ以上要る。そのときは、正規化の方法を見直す(既存の規格である RFC 8785 を使う案を比べる)。
- **見込み**: 半日。

### A2. sysinfo 1.1 を合成して、回路に収まるかを見る

- **確かめたいこと**: `design_id` のレジスタを足した回路が、9K と 4K に収まるか。値をビルドのときにどう渡すか。
- **仕様の章**: 5.5、5.6
- **手順**:
  1. `gateware/rtl/sysinfo.v` に、パラメータ `DESIGN_ID` と、オフセット `0xc` の読み取りを足す。版を `0x00010001` にする。
  2. 値の渡し方を 2 通り試す: yosys の `chparam -set DESIGN_ID` と、ビルドの前に生成するヘッダ(`` `define ``)。
  3. `tools/build_base.py` で、9K の base を合成と配置配線まで通す(実機には書かない)。足す前と後で、使った LUT とレジスタの数、最大動作周波数を比べる。
  4. シミュレーション(`uv run pytest -q -m sim`)に、`0xc` を読むと渡した値が返るテストを足す。
  5. 4K(base と camstream)でも同じ比較をする。4K は別のツール一式(oss-cad-suite)が要るので、環境が無ければ「未確認」と記録する。
- **通ったと言える条件**: 9K の base が配置配線を通り、シミュレーションで値が読める。増えた資源の数が記録されている。
- **やめる条件**: 4K の camstream で、足したぶんが原因で配置配線が通らなくなる。そのときは、識別値を `sys.version` の上位に畳むなど、レジスタを増やさない形を検討する。
- **見込み**: 半日から 1 日。

### A3. `.npq` を読む処理を書いて、いまのデザインを新形式で読む

- **確かめたいこと**: 仕様 5.1〜5.3 の項目で、同梱の 5 件を情報を落とさずに書けるか。ローダーの確認(仕様 5.7 の 1〜3)が書けるか。
- **仕様の章**: 5.1、5.2、5.3、5.7、6 章
- **手順**:
  1. いまの `manifest.yaml` から `.npq` を作る変換を書く(実験用の道具)。
  2. `.npq` を読む関数を書く: `format` の確認、`.fs` の sha256 の確認、識別値の再計算と比較。
  3. 同梱の 5 件を変換し、読んだ結果の `ips` が、いまの `load_manifest` の結果と同じになることを確かめる。
  4. 壊れた入力で、止まる場所とエラーの文面を確かめる: `format` が知らない値、`.fs` が違う、`ips` を 1 文字書き換えた、`*.npq` が 2 つある、`bitstream.file` がフォルダの外を指す。
- **通ったと言える条件**: 5 件とも、いまのローダーと同じ `ips` が得られる。壊れた入力は、どれも書き込みの前に止まる。
- **やめる条件**: いまの `manifest.yaml` にある情報で、新形式に置き場所が無いものが見つかる。そのときは、仕様 5.2 か 5.3 に項目を足してから続ける。
- **見込み**: 半日。

### A4. 厳しい検査の決まりで、A1 と A3 をやり直す(2026-11-18 に追加)

- **きっかけ**: A1 がやめる条件に当たり、仕様を「入力を厳しく検査し、直して読み進めない」形に書き直した(仕様 5.9 の V1 から V12)。
- **確かめたいこと**: 書き直した仕様の文章だけから Python と JavaScript の実装を書いて、すべての入力で、通す / 拒否するの判定、通したときの識別値、拒否したときの決まりの番号が一致するか。
- **仕様の章**: 5.2、5.3、5.4、5.7、5.9
- **手順**:
  1. 検査(V1 から V11)と識別値の計算を、Python と JavaScript の両方で書く。
  2. 通る入力と拒否する入力を 1 つのファイルにまとめ、両方の実装が同じファイルを読んで判定する。拒否する入力には、仕様 5.9 の例のすべてと、A1 で値が分かれた 6 種類を入れる。
  3. A3 と同じく、同梱の 5 件を `.npq` に変換して読み、いまのローダーと同じ `ips` になることを確かめる。
- **通ったと言える条件**: すべての入力で、判定、値、番号が一致する。仕様の計算例 3 つとも一致する。
- **やめる条件**: 合わせ込む前の食い違いが、仕様の文の読み方の違いで 3 つ以上残る。そのときは、検査の決まりを文章ではなく、機械が読める形(JSON Schema など)で持つ案を比べる。
- **A1 と A3 を 1 つにした理由**: 検査の決まりを 2 つの実装で共有する。別々に進めると、前回のように読み方が割れる。

### A5. 仕様の文だけを読んだ別の書き手の実装を、A4 の入力にかける(2026-11-18 に追加)

- **きっかけ**: A4 は通ったが、2 つの実装を同じ書き手が書いた。仕様に無くて書き手が決めた点が 25 あり、読み方の違いは表に出にくかった。
- **確かめたいこと**: 仕様の文だけから書いた実装が、A4 の 185 件の入力で同じ判定になるか。仕様の文の読み方の違いで食い違う入力が、何件あるか。
- **仕様の章**: 5.2、5.3、5.4、5.9
- **手順**:
  1. 別の書き手が、仕様の文書だけを読んで JavaScript の実装を書く。A4 のコード、A4 の入力、この計画の 4 章(A4 の結果)は読まない。書き終えたらコミットする。
  2. そのあとで、A4 の入力のファイルにかける。実装は直さずに、食い違いを全部一覧にする。
  3. 食い違いを分類する: 仕様の読み方の違い / 仕様の改訂によるずれ(A4 の期待値が古い)/ 書き手の誤り / 処理系の挙動。
- **通ったと言える条件**: 仕様の読み方の違いによる食い違いが 2 件以下。
- **やめる条件**: 仕様の読み方の違いによる食い違いが 3 件以上。そのときは、検査の決まりを文章ではなく、機械が読める形(JSON Schema など)と、共通の入力のファイルで持つ案を比べる。
- **限界**: 「読まない」という約束は、書き手の申告と、コミットの順序でしか確かめられない。

### A6. 入力のファイルを今の仕様で作り直し、3 つの実装を一致させる(2026-11-18 に追加)

- **きっかけ**: 仕様は A4 と A5 のたびに直したので、A4 の入力のファイル(185 件)と、A4・A5 のコードは、どれも今の仕様より古い。
- **確かめたいこと**: 今の仕様で、3 つの実装(A4 の Python、A4 の JavaScript、A5 の JavaScript)が、すべての入力で同じ判定になるか。今の仕様の文で、期待値が決まらない入力がどれだけ残っているか。
- **仕様の章**: 5.2、5.3、5.4、5.7、5.9
- **手順**:
  1. 入力の期待値を、1 件ずつ、今の仕様の文に照らして決め直す(実装の出力から写さない)。重複した項目、桁数、深さ、文字列の中の見かけだけの違反、A5 で比べられなかった 10 個の決め方の入力を足す。
  2. 仕様の文から期待値が決まらない入力は、「仕様で未決」として分ける。
  3. 3 つの実装を、別々の実装のまま、今の仕様に合わせて直す。直す前の食い違いの件数も残す。
  4. 通る入力を乱数で壊した入力(数千件)でも、3 つの判定が互いに一致することを確かめる。
- **通ったと言える条件**: 未決を除く全件で、3 つの実装の判定、識別値、決まりの番号が期待値と一致する。乱数の入力で、3 つが互いに食い違わない。
- **やめる条件**: 「仕様で未決」が 10 件を超える。そのときは、仕様の書き方(文章の表)そのものを見直す。
- **できあがるもの**: 仕様に付属する適合テストの候補(入力のファイルと、使い方)。本実装と、B2 のブラウザの実装が、これを使う。

## 3. B 群: 実機が要る実験

### B1. 9K に sysinfo 1.1 の base を書き込み、Python から識別値を読む

- **前提**: A2 が通っている。Tang Nano 9K がつながっている。
- **確かめたいこと**: 実機で `sys.version` が `0x00010001`、`sys.design_id` がファイルの値と同じになるか。古い回路(sysinfo 1.0)との見分けが、`sys.version` でできるか。
- **仕様の章**: 5.5、5.7、5.8
- **手順**:
  1. A2 の回路を 9K に書き込む。`sys.id`、`sys.version`、`sys.design_id` を読む。
  2. いまの同梱の base(sysinfo 1.0)を書き込み、同じ 3 つを読む(2026-11-18 の測定では、`0xc` は `0xdeadbeef` だった)。
  3. LED、ボタン、scratch が、足す前と同じに動くことを確かめる。往復時間を測る(足す前は 1.87 ms)。
- **通ったと言える条件**: 1.1 の回路で識別値が一致し、1.0 の回路は版で見分けられ、ほかの動作と往復時間が変わらない。
- **やめる条件**: 識別値が読めない、または読むたびに値が変わる。

### B2. 試作ページで `.npq` を選び、照合してからつなぐ

- **前提**: A1、A3、B1 が通っている。PR #22 の試作ページがある。
- **確かめたいこと**: 手元のファイルを選んでつなぐ操作が成り立つか。部品(LED、ボタン)を、決め打ちのアドレスではなく `.npq` の `ips` から作れるか。
- **仕様の章**: 5.1、5.7、5.8
- **手順**:
  1. 試作ページに、`.npq` を選ぶ入力を足す。ファイルの選択を `.npq` の拡張子で絞れるかを見る。
  2. 選んだファイルで、仕様 5.7 の 1、3、5、6 を行ってからつなぐ。
  3. LED とボタンの部品を、`ips` の `type` と `parameters.width` から作る。
  4. 古い回路(sysinfo 1.0)のボードにつなぎ、「つながない」表示になることを確かめる。
- **通ったと言える条件**: 正しい組み合わせではつながって操作でき、古い回路ではつながらず、理由が表示される。
- **やめる条件**: ブラウザでファイルを選ぶ操作が、利用者にとって手間になりすぎる(判断はオーナー)。そのときは、レジストリから取る流れを先に作る。

### B3. わざと違うデザインのボードにつなぐ

- **前提**: B2 が通っている。識別値の違うデザインが 2 つある(たとえば、base と、レジスタを 1 つ足した base)。
- **確かめたいこと**: 取り違えを実際に止められるか。
- **仕様の章**: 5.7
- **手順**:
  1. デザイン X を書き込み、デザイン Y の `.npq` で、Python(`download=False`)とブラウザの両方からつなぐ。
  2. どちらも、レジスタへの書き込みが 1 回も行われる前に止まることを、ログで確かめる。
- **通ったと言える条件**: 両方とも書き込みの前に止まり、表示が「別のデザインが載っている」と読める。
- **やめる条件**: なし(止まらなければ、照合の順序の誤りなので直す)。

### 実験で見つかった、仕様の外の事柄

仕様は変えないが、実装に入る前に片づけるか、判断が要るもの。

- **9K の base を、いまの道具で作り直すと、同梱の `.fs` と sha256 が合わない**(同梱は `3a2b9bec…`、作り直すと `f12bfd3e…`。A2)。原因は調べていない。同梱の 5 件を作り直すときに、再現性の扱いを決める必要がある。
- **`ip.py` の `register_map` は、書き込み専用(`wo`)のレジスタも含めて、すべてのレジスタを読む**(A3)。仕様 5.3 の「`wo` と `read_effect` のレジスタは勝手に読まない」とぶつかる。→ #32 で、読まないように直した。
- **`tangnano4k-camstream` のストリームは `register: "window"` を指すが、`window` という名前のレジスタは無い**(`parameters` の側にある。A3)。読むコードは無いので、いまは害が無い。
- **ストリームの `mtu` と `parameters` の大半は、ドライバが読んでいない**(読むのは `gpio.py` の `width` だけ。A3)。
- **iverilog がこの PC に無く、シミュレーションのテスト 16 件が実行できない**(A2)。CI では実行される。
- **`build-a2/` に、A2 の計測用のスクリプト、ログ、`.fs` が残っている**(作業ツリー `nanopynq-exp-a2`、コミットしていない)。

## 5. 順序と依存

```
A1 ─┬─ A4 ── A5 ── A6 ──┐
A3 ─┘                   ├── B2 ── B3
A2 ── B1 ───────────────┘
```

A1、A2、A3 は互いに独立で、どれからでも始められる。A4 は A1 と A3 の結果を受けたやり直し。B1 は A2 の回路を使う。B2 は A4(ブラウザでの検査と計算、ファイルの読み方)と B1(識別値を持つ回路)を使う。
