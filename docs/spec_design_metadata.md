# デザインのメタ情報ファイルの仕様(案)2026-11-18

状態: 案。実装はまだ無い。実験をしながら細部を詰め、そのつどこの文書を直す(計画は `docs/plan_design_metadata_experiments.md`)。issue は #24。

## 結論と要約

- **nanopynq は、ビットストリームと対になる自前のメタ情報ファイル(JSON)を持つ。** PYNQ の `.bit` と `.hwh` の組にあたる。FabricGate の `manifest.yaml` には頼らない。
- **メタ情報ファイルは、ビットストリームの sha256、通信の設定、IP とレジスタの定義、デザインの識別値を持つ。**
- **識別値は、IP とレジスタの定義から計算する 32 ビットの値。** 同じ値をビルドのときに回路(sysinfo の新しいレジスタ)にも入れる。ホストは、ボードから読んだ値とファイルの値を比べて、載っているデザインがファイルと合うかを確かめる。
- **FabricGate では、nanopynq ランタイムの成果物を「ビットストリームとメタ情報ファイルの組」にする(提案)。** `manifest.yaml` から `ips`、`transport`、`mtu` を外す。公開の契約の変更になるので、決めるのはオーナー。
- **形式、ファイル名、識別値の範囲、古いデザインの扱い、手元のファイルでの接続は、2026-11-18 にオーナーが決めた。名前の項目、`link` と `boards.yaml` の優先、`.npq` と `.fs` の名前の一致は、2026-11-20 に決めた(10 章)。** 細部は実験で詰める(11 章)。

## 1. 背景

### 1.1 いまの形

- デザインは `manifest.yaml` と `.fs` の組。`manifest.yaml` は `schema: fabricgate-platform/v1` で、FabricGate の Platform Manifest の形を借りている。
- `Overlay` は、書き込みの前に `.fs` の sha256 を `manifest.yaml` の値と比べる(`src/nanopynq/manifest.py`)。書き込みのあとに `sys.id` を読み、`0x4e505131`("NPQ1")であることを確かめる(`src/nanopynq/overlay.py`)。

### 1.2 困っていること

1. **ボードに載っているデザインが何かを確かめられない。** `sys.id` はどのデザインでも同じ値で、`sys.version` は sysinfo ブロックの版。ブラウザのパネル(#21、PR #22 の試作)は書き込みをしないので、別のデザインが載ったボードにつなぐと、別の回路のレジスタに書いてしまう。
2. **メタ情報が FabricGate の契約に縛られている。** 項目を足すたびに、FabricGate の公開の契約を変えることになる。
3. **同梱の `manifest.yaml` は、FabricGate の公開の契約を満たしていない。** 2026-11-18 に、同梱の 5 件すべてを公開リポの `NanopynqManifest` で検証して確かめた。5 件とも通らない。
   - `mtu` が必須だが、どのファイルにも無い。
   - `ips` の `type`、`parameters`、`addr_range`、レジスタの `access` は契約に無く、拒否される。契約の `IpBlock` は `base`、`registers`、`streams` だけ、`Register` は `offset` と `width` だけ。

   つまり、いまの `manifest.yaml` は形だけ FabricGate に似ていて、中身は既に nanopynq 独自になっている。

### 1.3 PYNQ はどうしているか

PYNQ は、載っているデザインを回路から読んで確かめていない。自分が最後に書き込んだものをホスト側のファイルに記録し、それと照合している(詳しくは #24 のコメント)。書き込む側と使う側が同じボード上の Linux なので、これで成り立つ。nanopynq のブラウザのパネルは、書き込みの記録を見られないので、この方法は使えない。

## 2. 要件、制約、やらないこと

要件:
- R1. nanopynq 単体(FabricGate 無し)で、メタ情報ファイルと `.fs` だけからデザインを使える。
- R2. ホストは、書き込みの前に、`.fs` がメタ情報ファイルの指すものかを確かめられる(いまと同じ)。
- R3. ホストは、書き込みをしなくても、ボードに載っているデザインがメタ情報ファイルと合うかを確かめられる。
- R4. Python とブラウザの両方で、同じファイルを同じ意味に読める。
- R5. いまの 5 件の同梱デザイン(ストリームを持つ `tangnano4k-camstream` を含む)を、情報を落とさずに書ける。

制約:
- 9K と 4K は回路の容量が小さい。識別のために足す回路は、レジスタ 1 個ぶんに留める。
- ビットストリームの sha256 は、ビットストリーム自身には入れられない。

やらないこと(この仕様の範囲外):
- ビットフィールド、単位、値の範囲、ボード上の部品との対応。後から足せるように、説明用の場所(`doc`)だけ決めておく。
- 書き込みの応答、誤り検出(#21 で、今回は足さないと判断した)。
- RTL とメタ情報を 1 つの定義から生成する仕組み。
- パネルの部品の決め方。

## 3. 代替案

- **案 A: nanopynq 独自のメタ情報ファイル(JSON)。** `.fs` と対になるファイルを nanopynq が定義する。FabricGate の `manifest.yaml` は、2 つのファイルを sha256 つきで指すだけにする。
- **案 B: 現状維持+最小の変更。** `ips` は `manifest.yaml` に置いたまま、識別値の項目だけを足す。FabricGate の契約に `type`、`access` などを足して、いまのずれも直す。
- **案 C: ボードが自分で名乗る。** メタ情報そのもの(圧縮したもの)を回路かフラッシュに入れ、ホストがボードから読む。ファイルは要らなくなる。

| 観点 | 案 A | 案 B | 案 C |
| --- | --- | --- | --- |
| 影響範囲 | nanopynq のローダー、ビルド、sysinfo、同梱 5 件。FabricGate は契約から項目を外し、成果物を 1 つ足す | nanopynq は sysinfo とローダーの一部。FabricGate は契約に項目を足す | 回路(ROM かフラッシュの読み出し)、ビルド、ホスト。FabricGate は変えない |
| 保守性 | メタ情報を nanopynq だけで変えられる。形式の版も nanopynq が持つ | 項目を足すたびに、公開リポ → registry の順の契約変更が要る | 回路とホストの両方に解釈の実装が要る。中身を見るのにボードが要る |
| YAGNI | 必要なものだけ。ファイルが 1 つ増える | 最小。ただし 1.2 の 2 と 3 が残る | いま要らない回路を足す。9K / 4K では容量が厳しい |
| リスク | 2 つのファイルに同じ情報(ボード、sha256)が載り、ずれ得る | nanopynq が FabricGate に依存し続け、単体で使えない(R1 を満たさない) | 容量不足で入らないデザインが出る。読み出しに時間がかかる |

## 4. 採用案と理由

**案 A を採る。** 決め手は保守性と R1。

- 案 B は、R1(単体で使える)を満たさない。1.2 の 3 のとおり、形は既に分かれているので、合わせ直すより分けるほうが実態に合う。
- 案 C は、いまの問題(載っているデザインの確認)にはレジスタ 1 個で足りるので過剰。将来、ファイルを持たないボードをつなぎたくなったら、案 A の上に足せる(識別値からファイルを引く、など)。

## 5. 仕様

### 5.1 ファイル

- 形式は JSON(UTF-8、BOM 無し)。
- 名前は `<名前>.npq`。中身は JSON で、拡張子だけが独自(Jupyter の `.ipynb` と同じ考え方)。`.fs` と同じフォルダに置く。例: `base.fs` と `base.npq`。
- 拡張子が `.json` でないので、エディタは自動では JSON として色分けしない。Web サーバーは JSON の種類(`application/json`)を付けずに返すことがある。読む側は、拡張子や種類の表示に頼らず、中身を JSON として読む。 ブラウザのファイルを選ぶ画面は、`.npq` の拡張子で絞り込めないことがある(Ubuntu の Chrome では、`accept=".npq"` を付けても、ほかのファイルが表示された)。どのファイルが選ばれても、検査(5.9)で止まる。
- 1 つのフォルダに `*.npq` は 1 つだけ。`Overlay` は、フォルダを渡されたらその 1 つを読む。2 つ以上あればエラーにする。ファイルを直接渡してもよい。

### 5.2 項目

読む側は、ここと 5.3 に書いた書き方を 1 つずつ確かめ、合わなければエラーにして、その先へ進まない(検査の決まりの一覧は 5.9)。

| 項目 | 必須 | 書き方 |
| --- | --- | --- |
| `format` | ○ | 文字列 `"nanopynq-design/2"` か `"nanopynq-design/1"` と完全に同じ。違えば、ほかの項目を見ずにエラーにする。書く道具は `/2` を書く(版の違いは 5.2.1) |
| `board` | ○ | `^[a-z0-9]([a-z0-9-]*[a-z0-9])?$` |
| `bitstream.file` | ○ | `.fs` のファイル名。`^[A-Za-z0-9_][A-Za-z0-9._-]*$` で、255 文字まで(フォルダの区切りは使えない。メタ情報ファイルと同じフォルダにあるファイルだけを指せる) |
| `bitstream.sha256` | ○ | `^[0-9a-f]{64}$` |
| `bitstream.family` | `/2` で ○ | FPGA のファミリ。`^[a-z0-9]+$`(いまのボードは `gw1n`、`gw2a`、`gw5a`)。書き込みの手順がこれで変わる。`/1` では書けない |
| `link.kind` | ○ | `"uart"` か `"jtag"` |
| `link.baudrate` | `uart` のとき ○ | 1 から 2^53 - 1 までの整数。`jtag` のときは書けない |
| `link.usb_vid`、`link.usb_pid` | `/2` で ○ | ボードのデバッガの USB の VID と PID。`^0x[0-9a-f]{4}$`(例: `"0x0403"`、`"0x6010"`)。`link.kind` が `uart` でも `jtag` でも書く(書き込みは、同じ USB の機器の JTAG を使う)。`/1` では書けない |
| `design_id` | ○ | `^0x[0-9a-f]{8}$`。`0x00000000` と `0xdeadbeef` は使えない(5.4) |
| `ips` | ○ | IP の定義(5.3)。1 個以上の項目を持つオブジェクト(V3)。`sys` を必ず含む(`sys` が無いときに当たる決まりは V10) |
| `name` | — | デザインの名前。文字列。識別値には含めない(10 章の 6) |
| `doc` | — | 人が読む説明。文字列(改行を含めてよい)。ホストの動作にも識別値にも影響しない |

- この文書の正規表現は、どれも文字列の全体に一致することを求める(末尾の改行だけが余っている文字列も合わない)。
- **外の道具が読む 3 つの項目は、形式の版が上がっても、名前と意味を変えない**: `format`(`nanopynq-design/` で始まる文字列)、`board`、`bitstream`(`file` と `sha256`)。FabricGate は、デザインを公開するときに、この 3 つだけを読んで、マニフェストと合っていることを確かめる(中身のほかの部分は解釈しない)。IP の定義など、ほかの部分は、nanopynq の都合で変えてよい。
- `bitstream` と `link` の中に、上に無い項目は書けない。
- いちばん上の階層に、上に無い項目があっても、読む側は無視する(形式の版を上げずに、説明用の項目を足せるようにするため)。識別値には関わらない。
- いちばん上の `name`、`doc`、知らない項目の中の文字列は、中身を検査しない(制御文字や、エスケープで書いた対になっていないサロゲートがあっても通す)。5.3 の文字列の決まりは、`ips` の中だけに当てはまる。ただし、読む前の本文に当てはめる決まり(V1)は、ここにも当てはまる。
- **ホストがボードにつなぐ、書き込むのに要る情報は、ここに入れる**(`link`、`bitstream.family`)。ビルドにだけ要る情報(デバイスの型番、合成と配置配線の引数、I/O の電圧、クロックの周波数)は、入れない(`boards.yaml` のまま)。ボードの表を持たない読み手(ブラウザのページなど)が、メタ情報ファイルと `.fs` だけで動けるようにするため(10 章の 10)。
- ファミリの書き方は開いている(知らない値でも、読む側はエラーにしない)。レジスタの読み書きは、ファミリによらないため。**書き込む側は、手順を知らないファミリを、何も消す前に断る。**
- `link`、`bitstream.family` と `boards.yaml` が食い違ったときの扱いは、10 章の 7 と 12。

#### 5.2.1 形式の版

| 版 | 違い |
| --- | --- |
| `nanopynq-design/1` | `bitstream.family`、`link.usb_vid`、`link.usb_pid` が無い(書くと V3)。ボードの表を持たない読み手は、このファイルの `.fs` をファミリに合わせて書き込めない |
| `nanopynq-design/2` | 上の 3 つが必須。ほかは `/1` と同じ |

- 読む側は、両方の版を読む。`/1` のファイルでは、足りない値を補わない(Python は `boards.yaml` の値を使う。ブラウザは、ファミリによる確認をせずに書き込む、または書き込まない)。
- `/1` だけを読む古い読み手は、`/2` のファイルを V2 で断る。
- 3 つの項目は回路に入らないので、識別値(5.4)には含めない。同じ `ips` なら、版が違っても `design_id` は同じ。

### 5.3 `ips`

IP の名前から定義への対応。いまの `manifest.yaml` の `ips` と同じ形で、`read_effect` と `doc` だけが新しい。

**IP と レジスタの階層は、項目の集合が閉じている。** 下の表に無い項目があれば、エラーにする。ホストと回路のやり取りに関わる項目を足すときは、形式の版(`format`)を上げる。`parameters` の中と、ストリームの定義の中だけは、IP ごとに項目が違うので開いている。

IP の項目:

| 項目 | 必須 | 書き方 |
| --- | --- | --- |
| `base` | ○ | ベースアドレス。16 進の文字列。4 の倍数 |
| `addr_range` | — | アドレスの幅。16 進の文字列。4 の倍数で 4 以上。省くと `0x1000` |
| `type` | ○ | `ベンダー:名前:版`。`^[a-z0-9_]+:[a-z0-9_]+:(0|[1-9][0-9]{0,3})\.(0|[1-9][0-9]{0,3})$`。版は「メジャー.マイナー」で、それぞれ 0 から 9999 までの整数として比べる(1.10 は 1.9 より新しい)。ドライバの選択に使う |
| `parameters` | — | IP ごとのパラメータ。名前から値への対応。値は整数、文字列、真偽値か、それらを並べたリスト(空のリストでもよい。リストの中にリストやオブジェクトは置けない) |
| `registers` | — | レジスタの定義。省くと空 |
| `streams` | — | ストリームの定義。省くと空 |
| `doc` | — | 説明。文字列。`ips` の中の文字列なので、制御文字は使えない(改行も使えない。長い説明は、いちばん上の `doc` に書く) |

レジスタの項目:

| 項目 | 必須 | 書き方 |
| --- | --- | --- |
| `offset` | ○ | ベースからのオフセット。16 進の文字列。4 の倍数で、`offset + 4` が `addr_range` を超えない |
| `width` | ○ | ビット幅。1 から 32 までの整数 |
| `access` | ○ | `"ro"`、`"rw"`、`"wo"` |
| `read_effect` | — | 真偽値。`true` なら、読むと回路の状態が変わる。省くと `false` |
| `doc` | — | 説明。文字列 |

ストリームの項目(開いている):

| 項目 | 必須 | 書き方 |
| --- | --- | --- |
| `dir` | ○ | `"read"` か `"write"` |
| `mtu` | ○ | 1 以上の整数(バイト) |
| `doc` | — | 説明。文字列 |
| そのほか | — | 名前は下の決まりに従う。値は整数、文字列、真偽値。識別値に含まれる |

IP をまたぐ決まり:

- IP のアドレスの範囲(`base` から `base + addr_range` の手前まで)は、互いに重ならない。`base + addr_range` は 2^32 を超えない。
- 1 つの IP の中で、2 つのレジスタが同じ `offset` を持たない。`offset` は値で比べる(`"0x4"` と `"0x04"` は同じ)。
- `sys` という名前の IP が必ずある。`base` は `0x0`(`0x0000` のように 0 を重ねてもよい)、`type` は `nanopynq:sysinfo:<版>`。レジスタ `id`(`offset` が 0、`ro`、32 ビット)と `version`(`offset` が 4、`ro`、32 ビット)を持つ。版が 1.1 以上なら `design_id`(`offset` が `0xc`、`ro`、32 ビット)も持つ。`id` と `version`、版が 1.1 以上のときの `design_id` に、`read_effect: true` は書けない(ホストが照合のために読むので)。`sys` のそれ以外は縛らない: ほかのレジスタ、`addr_range`、`parameters`、`streams` は、ふつうの IP と同じに書ける。版が 1.0 の `sys` に `design_id` という名前のレジスタがあっても、形も `read_effect` も問わない(ホストは 1.0 の回路の `design_id` を読まない)。

`ips` の中の、値の書き方の決まり:

| 対象 | 決まり | 決まりが無いと起きること(実験 A1) |
| --- | --- | --- |
| 名前(IP、レジスタ、ストリーム、パラメータ、ストリームの項目) | `^[a-z][a-z0-9_]*$`。`doc` は説明用に取ってあり、IP、レジスタ、ストリーム、パラメータの名前には使えない | ASCII 以外のキーで、並べる順が Python と JavaScript で違った |
| 整数 | JSON の整数で、-(2^53 - 1) から 2^53 - 1 まで | 2^53 を超えると JavaScript で丸まった |
| 16 進の文字列 | `base`、`addr_range`、`offset` は、必ず 16 進の文字列で書く(整数では書けない)。`^0x[0-9a-f]+$`(小文字)。値は 2^32 より小さい | `"0x1_000"` と `"0x10zz"` で結果が違った。`"1000"` を 16 進と読むか 10 進と読むかが決まっていなかった |
| 小数 | 使えない(`6.0`、`6e0`、`-0.0` も)。これは `ips` の中に限らず、ファイルのどこでも同じ(V1。下の「読む前の本文に当てはめる決まり」) | Python は `6.0` と `6` を区別し、JavaScript の素の `JSON.parse` は区別できない |
| `null` | 使えない。省くか、値を書く | 「省いた」と同じに扱うかが実装で違った |
| 文字列 | 正しい Unicode(対になっていないサロゲートは使えない)。制御文字(U+0000 から U+001F、U+007F)は使えない。ASCII 以外の文字は、値には使える | 壊れた文字列を Python はエラーにし、JavaScript は通した。制御文字は、JSON に直すときの書き方が実装に任されている |

`read_effect` について: `gateware/rtl` の各ブロックの冒頭にあるレジスタの説明を読んだ範囲では、読むと状態が変わるレジスタは見つからなかった(`i2c_master`、`uflash_reader`、`fb_display` は、説明からは判断できていない)。パネルは周期的に読むので、将来そういうレジスタができたときに、勝手に読まないための印として先に決めておく。ホストの決まり: `read_effect` が `true` のレジスタと `wo` のレジスタは、利用者が操作したとき以外は読まない。

読む前の本文に当てはめる決まり(V1。実験 A4、A5):

次の 3 つは、JSON として読んだあとの値ではなく、**読む前の本文に書かれたとおり**に当てはめる。読んだあとの値では、処理系によって見え方が違うため(実験 A5 で、ここの読み方の違いから 2 つの実装が割れた)。

- **数は、どこに書かれていても整数の書き方。** `-?(0|[1-9][0-9]{0,15})` に合うものだけ(小数点、指数、17 桁以上の数は使えない)。`ips` の中に限らず、いちばん上の知らない項目の中でも同じ。
- **同じオブジェクトの中に、同じ名前の項目を 2 つ書けない。** JSON としては読めてしまい、Python も JavaScript も後ろの値を採るが、前の値が検査をすり抜けるので、エラーにする。名前は、エスケープを解いたあとの文字の並びで比べる(`"a"` と `"\u0061"` は同じ名前)。Unicode の正規化はしない(見た目が同じでも、文字の並びが違えば別の名前)。
- **入れ子の深さは 64 まで。** オブジェクトと配列を 1 段と数え、いちばん上のオブジェクトを 1 とする。

実装の注意:

- JavaScript の素の `JSON.parse` は、`6.0` を `6` として読み、重複した項目の前の値を捨てる。どちらも、読んだあとでは分からない。読む前の本文を走査して確かめる(実験 A4 の計測では、1 MiB の本文で約 11 ms)。`JSON.parse` の reviver に渡る元の書き方(`context.source`)だけに頼る方法は、捨てられた値が見えないので使えない。
- Python の `json` は、JSON に無い値(`NaN`、`Infinity`)を読み、桁の多い整数で例外を出す。前者は JSON として読めないものとして V1、後者は上の「17 桁以上」で V1 になる。重複した項目は `object_pairs_hook` で検出できる。
- 16 桁までで、2^53 - 1 を超える整数(たとえば `9007199254740993`)は、V1 には当たらない。`ips` の中なら V4、`link.baudrate` なら V3 で止まる。それ以外の場所(いちばん上の知らない項目の中)では、無視される。

### 5.4 識別値(`design_id`)

識別値は、`ips` から計算する 32 ビットの値。ホストがボードと話すのに使う情報がすべて同じなら同じ値になり、どれかが違えば(ほぼ確実に)違う値になる。

計算の手順:

0. 5.2 と 5.3 の決まりをすべて確かめる(5.9)。1 つでも合わなければエラーにして、計算しない。
1. `ips` から、IP、レジスタ、ストリームの階層にある `doc` を取り除く。
2. IP ごとに、省いた項目を補い、アドレスを整数にする。それ以外は変えない。
   - `base`、`addr_range`、レジスタの `offset` は整数にする。`addr_range` を省いていれば `4096` にする。
   - `parameters`、`registers`、`streams` を省いていれば `{}` にする。
   - レジスタの `read_effect` を省いていれば `false` にする。
3. JSON に直す。キーは文字コードの順に並べ(名前は ASCII に限っているので、実装による順序の違いは出ない)、空白を入れず、区切りは `,` と `:`、整数は 10 進、真偽値は `true` と `false`、ASCII 以外はエスケープせず UTF-8 のまま。リストの中の順序は変えない。
4. そのバイト列の SHA-256 を取り、先頭の 4 バイトをビッグエンディアンの 32 ビットの整数として読む。
5. 結果が `0x00000000` か `0xdeadbeef` なら、ビルドをエラーにする(前者は「未設定」(5.5)、後者は割り当ての無いアドレスの読み取り値と区別できないため)。これは書く側のエラーで、検査の決まりの番号は無い。

手順 0 の検査を通った入力では、手順 2 のあとの形は 1 通りに決まる(IP は 6 項目、レジスタは 4 項目)。

計算例(6.1 の `tangnano9k-base`)。手順 3 のバイト列:

```
{"buttons":{"addr_range":4096,"base":8192,"parameters":{"width":2},"registers":{"data":{"access":"ro","offset":0,"read_effect":false,"width":2}},"streams":{},"type":"nanopynq:gpio_in:1.0"},"leds":{"addr_range":4096,"base":4096,"parameters":{"width":6},"registers":{"data":{"access":"rw","offset":0,"read_effect":false,"width":6}},"streams":{},"type":"nanopynq:gpio_out:1.0"},"sys":{"addr_range":4096,"base":0,"parameters":{},"registers":{"design_id":{"access":"ro","offset":12,"read_effect":false,"width":32},"id":{"access":"ro","offset":0,"read_effect":false,"width":32},"scratch":{"access":"rw","offset":8,"read_effect":false,"width":32},"version":{"access":"ro","offset":4,"read_effect":false,"width":32}},"streams":{},"type":"nanopynq:sysinfo:1.1"}}
```

この SHA-256 の先頭 4 バイトから、`design_id` は `0xabf78d8c` になる。

性質(計算して確かめた):
- `doc` を足しても値は変わらない。
- `buttons` の `base` を `0x3000` にすると値が変わる。
- **`tangnano9k-base` と `tangnano20k-base` は同じ値(`0xabf78d8c`)になる。** 2 つは IP の定義が同じため。識別値が表すのは「ホストから見た回路の形」で、ビルドやボードではない。ボードの取り違えは、書き込みのときの IDCODE の確認(nanopynq の書き込みの手順、`nanopynq.gowin`。#49 の前は openFPGALoader)と `board` の項目で防ぐ。`tangnano4k-base`(LED が 1 個)は `0x79d574b7`。

### 5.5 回路の側: sysinfo 1.1

- `sys` に、読み取り専用のレジスタ `design_id` を足す。オフセットは `0xc`、32 ビット。
- `sys.version` は `0x00010001`(1.1)にする。上位 16 ビットがメジャー、下位 16 ビットがマイナー。
- `type` は `nanopynq:sysinfo:1.1`。
- 値は、ビルドのときに top のパラメータ `DESIGN_ID` として渡し、sysinfo まで通す。渡し方は yosys の `chparam -set DESIGN_ID 32'h<値> top` にする(実験 A2)。パラメータの無い top に渡すと yosys がエラーで止まるので、渡し先の間違いに気づける。マクロ(`-D`)や生成したヘッダは、渡し忘れると黙って 0 になるので採らない。
- 値を渡さずに作った回路は、版が 1.1 で `design_id` が `0x00000000` になる。`0x00000000` は「未設定」を表す。ホストは、未設定を「合わない」として扱う。
- sysinfo 1.1 では、`0xc` は sysinfo が答える。割り当ての無いアドレスの値(`0xdeadbeef`)が返るのは `0x10` から。
- 回路の大きさ(実験 A2、9K の base、配置配線後): LUT は 462 から 446、フリップフロップは 266 のまま。足したことで大きくはならなかった。4K と 20K の配置配線は未確認。

### 5.6 ビルドの順序

識別値は `.fs` の中に入り、`.fs` の sha256 はメタ情報ファイルに入る。循環しないように、次の順にする。

1. `ips` を決める。
2. `ips` から `design_id` を計算する。
3. `design_id` を回路に入れて、`.fs` を作る。
4. `.fs` の sha256 を計算する。
5. `format`、`board`、`bitstream`、`link`、`design_id`、`ips` をメタ情報ファイルに書く。`bitstream.family` と `link` の値は、`boards.yaml` から書き写す(`programmer.family`、`host_link` の `usb_vid` と `usb_pid`、UART の baudrate)。

`design_id` は `bitstream.sha256` にも自分自身にも依存しない。

書き出すファイルの形(項目の順、字下げ、改行)は、この仕様では決めない。読む側は、形に頼らない。同じ入力から同じバイト列を書くことは、書く道具の側で保つ。

### 5.7 ホストの照合の順序

`Overlay` が行う確認を、順に並べる。どれかが合わなければ、その先へ進まない。

1. メタ情報ファイルを見つけて読み、5.9 の V1 から V10 を確かめる。
2. `ips` から識別値を計算し、`design_id` と比べる(V11。ファイルが手で書き換えられていないかの確認)。
3. `.fs` の sha256 を `bitstream.sha256` と比べる(V12。いまと同じ。`.fs` が無いときも V12)。`download=False` では確かめない(`.fs` を読まず、無くてもよい)。
4. `download=True` なら書き込む。
5. `sys.id` が `0x4e505131` であることを確かめる(いまと同じ)。
6. `sys.version` を読む。1.1 以上なら `sys.design_id` を読み、`design_id` と比べる。読んだ値が `0x00000000`(未設定)なら、合わないものとして扱う。

ブラウザのパネルは、1、2、5、6 を行う(`.fs` を読まず、書き込みもしないので、3 と 4 は無い)。

### 5.8 古いデザイン(sysinfo 1.0)

sysinfo 1.0 の回路は、`0xc` を読むと `0xdeadbeef` を返す(実機で確かめた)。この値で判断せず、`sys.version` で判断する。

ファイルが宣言する版(`sys` の `type`)と、ボードが返す版(`sys.version`)の組み合わせごとの扱い。`Overlay` の `download` が `True` でも `False` でも、照合の結果は同じ。違うのは、照合できないときに警告を出すかどうかだけ。

| ファイル | ボード | 扱い |
| --- | --- | --- |
| 1.1 以上 | 1.1 以上 | `sys.design_id` を読み、ファイルの `design_id` と比べる。合わなければエラー(`0x00000000` も合わない) |
| 1.1 以上 | 1.0 | エラー。ファイルが識別値を持つと言っているのに、回路が持っていない(別のデザインか、古い回路が載っている) |
| 1.0(`.npq`) | 1.1 以上 | `sys.design_id` を読み、ファイルの `design_id` と比べる(5.7 の 6 は、ボードの版だけで決める) |
| 1.0(`.npq`) | 1.0 | 照合できない。`download=True` はそのまま使える(自分で書き込んだ直後なので、いまと同じ確かさがある)。`download=False` は、照合できていないと警告して続ける |
| `manifest.yaml`(移行のあいだ) | どれでも | 照合しない(`sys.id` だけを確かめる)。`download=False` は、照合できていないと警告して続ける |

エラーのときは、`sys` 以外のレジスタに触る前に、通信を閉じてから止まる。

ブラウザのパネルは、照合できない組み合わせ(下の 2 行)では、つながない。「このボードのデザインは識別値を持たない。作り直すか、Python から使う」と表示する。

移行のあいだ、`Overlay` は `*.npq` が無ければ、いまの `manifest.yaml` を読む。同梱の 5 件を作り直したら、この読み方を外す。

### 5.9 検査の決まり(一覧)

読む側(Python、ブラウザ)は、次を番号の順に確かめる。1 つの決まりを、ファイルの全体について確かめ終えてから、次の決まりへ進む。1 つでも合わなければ、その決まりの番号と、合わなかった項目の場所(例: `ips.leds.registers.data.width`)を示してエラーにする。複数の決まりに合わない入力では、**番号がいちばん小さい決まり**を示す。決まりの番号は、どの実装でも同じでなければならない。場所は、利用者への手がかりで、実装によって違ってよい(同じ決まりに 2 か所で合わないとき、どちらを示すかは決めない)。**直して読み進めること(大文字を小文字にする、足りない項目を補う、など)はしない。** 省略できると書いた項目を補うことだけが例外。

| 番号 | 決まり | 章 |
| --- | --- | --- |
| V1 | ファイルは 1 MiB(1048576 バイト)以下で、UTF-8(BOM 無し)の JSON として読め(`NaN` と `Infinity` は JSON ではない)、いちばん上はオブジェクト。読む前の本文で、数はどこでも 16 桁までの整数の書き方、同じオブジェクトの中に同じ名前の項目が無い、入れ子の深さは 64 まで | 5.1、5.3 |
| V2 | `format` が `"nanopynq-design/1"` か `"nanopynq-design/2"` と完全に同じ(`format` が無いときも、この決まり) | 5.2 |
| V3 | いちばん上の必須の項目がそろい、それぞれの書き方に合う。`bitstream` と `link` に余計な項目が無い(項目の集合は `format` の版で決まる。5.2.1)。`name` と `doc` は、あれば文字列。`ips` は、1 個以上の項目を持つオブジェクト | 5.2 |
| V4 | `ips` の中の値(場所を問わない)に、`null`、範囲の外の整数、壊れた文字列、制御文字が無い。項目の名前は、ここでは見ない(V5、V6) | 5.3 |
| V5 | 名前がすべて `^[a-z][a-z0-9_]*$` に合い、`doc` を名前に使っていない | 5.3 |
| V6 | IP、`parameters`、`registers`、`streams`、レジスタが、それぞれオブジェクト。IP とレジスタの階層に、表に無い項目が無い。必須の項目がそろっている | 5.3 |
| V7 | `base`、`addr_range`、`offset` が 16 進の文字列で、4 の倍数で、範囲に収まる(`addr_range` は 4 以上、`offset + 4` は `addr_range` 以下、`base + addr_range` は 2^32 以下) | 5.3 |
| V8 | `type`、`width`、`access`、`read_effect`、`doc`、パラメータの値、ストリーム(オブジェクトで、`dir` と `mtu` があり、項目の値が整数、文字列、真偽値)が、それぞれの書き方に合う | 5.3 |
| V9 | IP のアドレスの範囲が重ならない。続けて、1 つの IP の中でレジスタの `offset` が重ならない | 5.3 |
| V10 | `sys` があり、決まった形をしている(`sys` が無いときも、この決まり)。`id` と `version` に `read_effect: true` が無い。版が 1.1 以上なら、`design_id` にも無い(版が 1.0 の `design_id` は、形も `read_effect` も問わない) | 5.3 |
| V11 | `ips` から計算した識別値が `design_id` と同じ(計算した値が `0x00000000` や `0xdeadbeef` になる場合も、`design_id` にその値は書けない(V3)ので、読む側では必ずここで合わなくなる) | 5.4 |
| V12 | `.fs` があり、その sha256 が `bitstream.sha256` と同じ(Python だけ。ブラウザは `.fs` を読まない) | 5.7 |

V4 と V8 の境目: V4 は値の種類を見る(どの項目かは問わない)。V8 は、決まった項目の型と書き方を見る。例: `width` が `null` なら V4、`true` や `33` なら V8、2^53(16 桁で、範囲の外)なら V4。小数と 17 桁以上の整数(2^60 など)は V1 で、V4 より前に止まる。

拒否する入力の例(どれも、直さずにエラーにする):

| 入力 | 当たる決まり |
| --- | --- |
| `"format": "nanopynq-design/3"` | V2 |
| `"format": "nanopynq-design/2"` で、`bitstream.family` や `link.usb_vid` が無い | V3 |
| `"format": "nanopynq-design/1"` で、`bitstream.family` や `link.usb_vid` がある | V3 |
| `"usb_vid": 1027`、`"usb_vid": "0x04B4"`、`"usb_vid": "0x403"`、`"family": "GW1N"` | V3 |
| `"bitstream": {"file": "../base.fs", ...}` | V3 |
| `"sha256"` や `"design_id"` に大文字がある | V3 |
| `"link": {"kind": "jtag", "baudrate": 115200}` | V3 |
| `"parameters": {"width": 6.0}`、`"baudrate": 115200.0`、いちばん上の知らない項目の中の `2.5` | V1 |
| `"width": 6.0, "width": 6`(重複。後ろの値は正しい) | V1 |
| 17 桁以上の整数(場所を問わない) | V1 |
| `"parameters": null` | V4 |
| `"parameters": {"n": 9007199254740993}` | V4 |
| IP の名前が `LEDs`、`led-0`、`doc`、全角の文字 | V5 |

| `"width": 0`、`"width": 33`、`"access": "rc"`、`"read_effect": 1` | V8 |
| `leds` と `buttons` が同じ `base` | V9 |
| `sys` が無い、`sys.registers.id.offset` が `0x10`、`sys.registers.id` に `read_effect: true` | V10 |
| `sys.registers.id.offset` が `0x4`(`version` と同じ `offset` になる) | V9 |
| `ips` を書き換えて `design_id` を直していない | V11 |

2026-11-18 に、同梱の 5 件の `ips` が V5 から V10 をすべて満たすことを確かめた。同梱外のデザイン(`tools/build_base.py` のテンプレート)は、`type` と 16 進の書き方とパラメータの形だけを確かめた。

## 7. セルフ反論

> **反論 1**: 識別値は `ips` から作るので、RTL のアドレスを書き間違えても、ファイルと回路の識別値は一致する。確かめているのは「同じファイルから作った」ことだけではないか。
> **応答**: 当たる。識別値が防ぐのは「別のデザインが載ったボードにつなぐ」取り違えで、「メタ情報が回路と合っていない」誤りは防がない。後者は、デザインごとの実機の確認(いまも行っている)で防ぐ。根本の対策は、RTL とメタ情報を 1 つの定義から作ることだが、範囲外にした。

> **反論 2**: FabricGate で配るとき、`manifest.yaml` とメタ情報ファイルの両方に、ボードと `.fs` の sha256 が載る。ずれたらどちらが正しいのか。
> **応答**: 当たるので、役割を決める。nanopynq はメタ情報ファイルだけを読み、`manifest.yaml` は読まない。FabricGate は push のときに、2 つのファイルのボードが同じことを確かめる(8 章)。`.fs` の sha256 は、どちらも実際のファイルと比べるので、ずれていればどちらかの確認で止まる。

> **反論 3**: 32 ビットでは、別のデザインがたまたま同じ値になり得る。
> **応答**: 防ぎたいのは取り違えで、悪意のある偽装ではない。違うデザインが同じ値になる確率は、1 組あたり約 43 億分の 1。レジスタ 1 個で読めることのほうを優先した。偽装を防ぐ必要が出たら、幅を広げるのではなく、署名など別の仕組みが要る。

> **反論 4**: 9K と 20K の base が同じ識別値になる。パネルが 9K のファイルで 20K を操作してしまう。
> **応答**: IP の定義が同じなら、その操作は安全に行える(同じアドレスに同じ意味のレジスタがある)。ただし、通信の方式が違う(9K は UART、20K は JTAG)ので、実際には 9K のファイルで 20K にはつながらない。ボードの違いを識別値に含める案もあるが、「同じ回路を別のボードに載せたら値が変わる」ことの利点が見当たらないので、含めなかった(10 章の 3 で、含めないと決まった)。

> **反論 5**: JSON は、手で書くには YAML より面倒。
> **応答**: メタ情報ファイルはビルドの道具が書く(いまの `tools/build_base.py` も `manifest.yaml` をテンプレートから書いている)。読む側は、ブラウザが標準の機能だけで読めることを優先した。

> **反論 6**: IP とレジスタの項目を閉じると、項目を 1 つ足すだけで形式の版を上げることになり、古い読み手は新しいファイルを読めなくなる。厳しすぎないか。
> **応答**: 当たるが、意図している。この階層の項目は、ホストが回路とどう話すかを決める。古い読み手が知らない項目を黙って無視すると、「読むと状態が変わる」のような印を見落として操作してしまう。読めないほうが安全。説明用の項目は、いちばん上の階層と `doc` に置けるので、版を上げずに足せる。開いた場所(`parameters` とストリーム)は、名前と値の書き方を限ったうえで識別値に含めているので、2 つの実装で結果が分かれない。

> **反論 7**: 「直して読み進めない」と、手で書いたファイルの小さな書き間違い(大文字の 16 進など)でも読めない。
> **応答**: 当たるが、直し方を実装ごとに決めると、Python とブラウザで結果が分かれる(実験 A1 で実際に分かれた)。メタ情報ファイルはビルドの道具が書くもので、手で書く場面は少ない。エラーには決まりの番号と場所を出すので、直すのは難しくない。

## 8. FabricGate への提案(決めるのはオーナー)

公開の契約の変更になる。ここでは提案だけを書く。レポートが引いている「設計書 4.7」(ハブ側の変更はユーザーが行う、という記述)は、このリポジトリに無く、読めていない。

- **成果物**: nanopynq ランタイムの `artifacts` を、`bitstream` と `metadata`(メタ情報ファイル)の 2 つにする。pynq ランタイムの `bitstream` と `hwh` の組と同じ扱い。
- **`NanopynqManifest` から外すもの**: `ips`、`transport`、`mtu`。registry はメタ情報ファイルの中身を解釈しない。
- **push のときの確認**: メタ情報ファイルが JSON として読めること、`format` が `nanopynq-design/` で始まること、`board` が `manifest.yaml` と同じこと、`bitstream.sha256` が `.fs` と合うこと。
- **`fabricgate build`**: nanopynq ランタイムを、メタ情報ファイルを渡す形で選べるようにする(いまは「hwh からは `transport` と `mtu` が分からない」ため、選択肢から外されている)。
- **壊れるもの**: 契約からの削除なので破壊的な変更。2026-11-18 に本番の API で確かめた時点で、nanopynq ランタイムのデザインは 0 件(`GET /api/v1/designs?runtime=nanopynq` の `total` が 0)。登録を始める前に変えれば、移行するデータは無い。
- **できなくなること**: registry は IP の一覧を知らなくなるので、IP の種類での検索はできない。要るようになったら、公開のときに要約を取り出す形で足す。
